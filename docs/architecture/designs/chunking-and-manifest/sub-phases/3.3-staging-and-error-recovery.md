## Deliverables

1. Staging directory path resolution in `src-tauri/src/storage/staging.rs`: `%APPDATA%/arx-runa/staging/` on Windows, `~/.local/share/arx-runa/staging/` on Linux; auto-create on first access if absent
2. Orphan blob cleanup function `cleanup_orphaned_blobs(staging_directory: &Path, sqlcipher_store: &SqlCipherMetadataStore) -> Result<usize, StorageError>`: scan staging for `*.blob` files, query SQLCipher directly (`SELECT blob_name FROM chunks`) for all known blob names, delete files whose stem does not appear in the known set, return count of deleted files
3. `cleanup_orphaned_blobs` called during vault open, before any user-facing operation
4. SQLCipher transaction wrapping confirmed for all manifest mutations: `insert_node` + `insert_chunks` in one transaction, `delete_node` + CASCADE in one transaction (enforced in `SqlCipherMetadataStore`, verified by test)
5. File deletion flow in `src-tauri/src/storage/vault_ops.rs`: read chunk `blob_name` values → begin transaction → delete node row (CASCADE removes chunk rows) → commit → delete blob files from staging
6. Crash recovery test coverage: interrupt after encrypt but before commit (simulate by aborting the transaction) — confirm no manifest entry exists and orphan cleanup removes the staging blobs; interrupt after commit but before blob deletion — confirm orphan scan is a no-op (blobs are still referenced) and next explicit delete cleans up correctly
7. Test suite covering: orphan cleanup removes untracked blobs, orphan cleanup preserves blobs whose `blob_name` is present in the manifest, transaction rollback on partial encrypt failure leaves no manifest entry, 0-byte file deletion (node-only deletion, no blob files), staging directory is created automatically if absent

## Validation Checkpoint

**Automated tests**:
```bash
cargo test storage::staging
```
All tests must pass.

**Manual verification**:
- Create staging blobs manually (copy any file and rename to `<uuid>.blob`); open vault — confirm orphan blobs are removed and a valid blob referenced by the manifest is not touched
- Kill the process (via task manager or `kill -9`) during a file encrypt operation; restart vault — confirm no partial entry appears in the file list and the staging directory contains no orphaned blobs

**Acceptance criteria**:
- Orphan cleanup runs on every vault open and removes all blobs not referenced by any `chunks.blob_name` entry
- Orphan cleanup never deletes a blob that is referenced in the manifest
- All manifest mutations are transactional — partial states are not observable
- The staging directory is auto-created; the application does not fail if the directory did not exist at startup

## Implementation Notes

- Platform path resolution: use `dirs::data_dir()` (from the `dirs` crate) as the base; append `arx-runa/staging`. This resolves correctly on both Windows (`%APPDATA%`) and Linux (`~/.local/share`).
- Orphan scan reads all files in the staging directory matching `*.blob`, strips the extension to obtain the UUID string, and checks membership against the set of `blob_name` values returned by a SQLCipher query (`SELECT blob_name FROM chunks`). Do not parse the UUID — a string equality check on the stem is sufficient and avoids parsing errors on unexpected filenames.
- Files with unexpected extensions or names that are not valid UUIDs should be left untouched by the orphan scan (do not delete them — they may be unrelated application files if the staging directory path is misconfigured).
- Transaction correctness in `SqlCipherMetadataStore`: `insert_node` and `insert_chunks` must be called within the same `BEGIN`/`COMMIT` block. The calling code in `vault_ops.rs` is responsible for starting and committing the transaction; the trait methods execute within the active transaction.
- File deletion order: read `blob_name` values first (before the transaction), then delete the manifest entry, then delete blob files after commit. If blob file deletion fails after a successful commit, the files become orphans and are cleaned up on next startup — this is the designed recovery path.

## Security Review

**Not required** — staging blobs are AEAD ciphertext (XChaCha20-Poly1305). Leaving orphaned blobs on disk does not expose plaintext. No cryptographic operations are introduced in this sub-phase.

## Completion

This is the final sub-phase for Phase 3 (Chunking and Manifest). After completion:
- The local storage layer is fully operational: files can be encrypted into padded chunks, stored in the SQLCipher manifest, and decrypted back to their original form
- The staging directory is managed automatically with crash-safe orphan cleanup
- All manifest mutations are transactional — no partial state is observable after a crash
- Phase 4 (Cloud Synchronisation) can begin: the `CloudTransport` layer will read blobs from the staging directory and upload them to the configured cloud backend
