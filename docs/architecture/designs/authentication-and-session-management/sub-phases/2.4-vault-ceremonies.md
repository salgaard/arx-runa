## Deliverables

1. **Vault creation** (`create_vault` in `src-tauri/src/auth/ceremonies.rs`) — 21-step ceremony:
   - [If Tier 2] Generate 32-byte key file via CSPRNG; write to user-chosen USB path
   - [If Tier 2] Compute `key_file_blake3 = blake3::hash(key_file_content)`
   - Generate 32-byte salt via CSPRNG; generate `vault_id` (UUID v4)
   - Argon2id + HKDF → `key_encryption_key`, `sqlcipher_key`, `manifest_key`; zeroize `master_key`
   - Create SQLCipher DB with `sqlcipher_key`; apply Phase 3.1 schema
   - Generate X25519 identity keypair; wrap X25519 private key with `key_encryption_key`; store in SQLCipher
   - Write vault header JSON to local staging and upload via `CloudTransport`
   - Begin session: store `SessionKeys` in `SessionManager`
2. **Password change** (`change_password` in `src-tauri/src/auth/ceremonies.rs`):
   - Authenticate with current credentials → acquire current `SessionKeys`; re-derive `master_key` from current credentials
   - Accept new password; [If Tier 2] require USB key file to be present
   - [If `recovery_slots` non-empty] Prompt for recovery phrase; validate BIP-39 checksum; derive `recovery_key`; decrypt slot to verify it yields current `master_key` (integrity check); if phrase unavailable, remove `recovery_slots`
   - Generate new salt (mandatory); Argon2id + HKDF → new keys
   - Re-wrap all `file_key` values: decrypt with old `key_encryption_key`, encrypt with new `key_encryption_key`
   - Re-wrap X25519 private key: decrypt with old, encrypt with new `key_encryption_key`
   - Re-key SQLCipher: `PRAGMA rekey = '<new_sqlcipher_key>'`
   - [If recovery slot re-wrap succeeded] Re-encrypt: `new_wrapped_master_key` = XChaCha20-Poly1305.encrypt(new_master_key, recovery_key, aad); update `recovery_slots[0].wrapped_master_key`; zeroize `recovery_key`
   - Zeroize new `master_key`
   - Update vault header (new salt, same `key_file_blake3`, updated `recovery_slots`); upload to cloud
   - Replace `SessionKeys` with new derived keys; zero old keys
3. **USB key file rotation** (`rotate_key_file` in `src-tauri/src/auth/ceremonies.rs`):
   - Authenticate with current credentials (requires old key file to be present); re-derive `master_key`
   - [If `recovery_slots` non-empty] Prompt for recovery phrase (same verification flow as `change_password`)
   - Generate new 32-byte key file; write to new USB location
   - Generate new salt (mandatory); Argon2id + HKDF → new keys
   - Re-wrap all `file_key` values and X25519 private key (same steps as password change)
   - Re-key SQLCipher: `PRAGMA rekey = '<new_sqlcipher_key>'`
   - [If recovery slot re-wrap succeeded] Re-encrypt `new_master_key` into `recovery_slots[0].wrapped_master_key`; zeroize `recovery_key`
   - Zeroize new `master_key`
   - Update vault header (new salt, new `key_file_blake3`, updated `recovery_slots`); upload to cloud
   - Replace `SessionKeys`; zero old keys
4. **New-device recovery** (`recover_vault` in `src-tauri/src/auth/ceremonies.rs`):
   - Accept Rclone remote configuration
   - Fetch vault header from cloud; parse salt, argon2_params, `key_file_blake3`
   - [If Tier 2] Accept USB key file (auto-detection or manual selection)
   - Accept password; Argon2id + HKDF → session keys; zeroize `master_key`
   - Fetch encrypted manifest backup from cloud; decrypt with `manifest_key`
   - Import manifest into local SQLCipher (keyed with `sqlcipher_key`)
   - Begin session
5. **Recovery slot setup** (`setup_recovery` in `src-tauri/src/auth/ceremonies.rs`):
   - Re-authenticate: accept current password + [If Tier 2] USB key file → Argon2id + HKDF → re-derive `master_key`
   - Generate 256-bit recovery entropy via CSPRNG; BIP-39 encode → 24-word phrase
   - Generate 32-byte `recovery_salt` via CSPRNG
   - Derive `recovery_key` = Argon2id(phrase_words_space_joined, recovery_salt, same_params)
   - Wrap: `wrapped_master_key` = XChaCha20-Poly1305.encrypt(master_key, recovery_key, aad=`b"arx-runa recovery v1" || vault_id_bytes`)
   - Zeroize `master_key` and `recovery_key`
   - Append `RecoverySlot { method: "bip39", argon2_salt, argon2_params, wrapped_master_key }` to `recovery_slots` in vault header; upload to cloud
   - Return 24-word phrase to UI (the only time it leaves the ceremony); UI displays and requires acknowledgement; phrase zeroed from UI memory after acknowledgement
6. **Recovery with phrase** (`recover_with_phrase` in `src-tauri/src/auth/ceremonies.rs`):
   - Accept 24-word recovery phrase
   - Validate BIP-39 checksum; return `InvalidRecoveryPhrase` immediately if invalid (no Argon2id runs)
   - Fetch vault header; if `recovery_slots` is empty: return `NoRecoverySlot`
   - For each slot where `method == "bip39"`:
     - Derive `recovery_key` = Argon2id(phrase, slot.argon2_salt, slot.argon2_params)
     - Attempt XChaCha20-Poly1305.decrypt(slot.wrapped_master_key, recovery_key, aad)
     - On success: break
   - If all slots fail: return `InvalidCredentials`
   - HKDF(master_key) → `key_encryption_key`, `sqlcipher_key`, `manifest_key`; zeroize `master_key`
   - Session begins; prompt user to set a new password (calls `change_password` internally, with `recovery_key` available for slot re-wrap)
7. Critical invariant enforced in all flows: `master_key` must not be assigned to a struct field, returned, or passed to a function that might store it — it lives only within ceremony-local scope and is zeroized immediately after all dependent operations complete (HKDF and, when present, recovery slot re-wrap)
8. Key property documented in code: encrypted cloud blobs are never touched during password change or key file rotation — only key wrapping changes (no chunk re-encryption)
9. Sharing relationships survive rotation: X25519 keypair is re-wrapped, not regenerated; assertion in tests confirms public key is identical before and after rotation
10. Tests:
   - Vault creation produces a vault header JSON with correct fields including `recovery_slots: []`; SQLCipher DB opens with derived `sqlcipher_key`
   - Password change: old `key_encryption_key` cannot unwrap file_keys after change; new `key_encryption_key` can
   - Password change: SQLCipher DB opens with new `sqlcipher_key` and not with old `sqlcipher_key`
   - Password change with recovery slot: slot `wrapped_master_key` differs before and after (re-wrapped); phrase still unlocks vault after change
   - Password change without providing phrase: `recovery_slots` is empty after change
   - Key file rotation: X25519 public key is identical before and after rotation
   - Key file rotation: old `key_file_blake3` in vault header differs from new `key_file_blake3`
   - Key file rotation with recovery slot: slot re-wrapped; phrase still unlocks vault after rotation
   - New-device recovery: reconstructs operational vault from cloud vault header + manifest backup
   - `setup_recovery`: vault header gains one `bip39` recovery slot; `wrapped_master_key` decodes to 72 bytes
   - `recover_with_phrase` with correct phrase: vault unlocks, session active
   - `recover_with_phrase` with wrong phrase: returns `InvalidCredentials`
   - `recover_with_phrase` with invalid BIP-39 checksum: returns `InvalidRecoveryPhrase` before any Argon2id runs
   - `recover_with_phrase` when no recovery slots configured: returns `NoRecoverySlot`
   - All flows: `master_key` does not appear in any struct after the derivation step (inspected via field enumeration in tests)
   - Recovery phrase is not logged, stored in any persistent location, or returned from any function other than `setup_recovery`

## Validation Checkpoint

**Automated tests**:
```bash
cargo test auth::vault
```
All tests must pass.

**Manual verification**:
- Full vault creation on a real machine with a USB drive present; confirm key file written to USB, vault header uploaded to cloud, session active
- Password change: confirm old credentials rejected and new credentials accepted after change
- New-device recovery: on a second machine, configure Rclone remote, insert USB key file, enter password; confirm vault is fully operational

**Security check** (before marking complete):
- Confirm no test or production path stores `master_key` in a named field or returns it from `create_vault` / `change_password` / `rotate_key_file`
- Confirm vault header JSON does not contain `key_encryption_key`, `sqlcipher_key`, or `manifest_key` — only `tier`, `argon2_salt`, `argon2_params`, `key_file_blake3`, `vault_id`, `schema_version`, `recovery_slots`

**Acceptance criteria**:
- All six ceremony functions produce correct results verified by automated tests
- `master_key` lifetime is bounded in all flows
- Password change and key file rotation leave cloud blobs unchanged (no re-upload of encrypted chunks)
- X25519 public key is preserved across key file rotation
- Recovery phrase unlocks vault regardless of authentication tier
- Recovery slot survives password change and key rotation when phrase is provided
- Recovery slot is cleared when phrase is not provided during password change or key rotation

## Implementation Notes

- `create_vault` should validate that the target USB path exists and is writable before generating key material — avoid generating a key file that cannot be written
- Use the [Vault Creation Flow](../design.md#vault-creation-flow) from `design.md` for the exact vault header JSON schema (Tier 1 and Tier 2 formats). The header contains no derived key material — `key_encryption_key`, `sqlcipher_key`, and `manifest_key` must never appear in it
- The re-wrapping loop in `change_password` and `rotate_key_file` operates on every `file_key_wrapped` row in the SQLCipher `nodes` table — ensure it runs inside a transaction so partial failure does not corrupt key state
- `PRAGMA rekey` must be issued while the DB connection is open with the old key, before the old `sqlcipher_key` is zeroed
- In `recover_vault`, the manifest backup is decrypted entirely in memory before importing to SQLCipher (same exception as Phase 4.4 — typical manifest size < 10 MiB)
- Cross-phase dependency: if Phase 3.1 is not yet complete when Phase 2.4 is implemented, use a minimal stub schema (`CREATE TABLE _phase_stub (id INTEGER PRIMARY KEY)`) to allow the vault creation flow to be tested end-to-end; replace with the real schema once Phase 3.1 is merged

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- Ceremony correctness: all six flows zeroize `master_key` on every code path including error returns
- Re-wrapping logic: confirm old key material is zeroed after re-wrapping completes; confirm the re-key transaction is atomic
- `master_key` lifetime: confirm no compiler optimisation can hoist the `master_key` variable beyond its intended scope (use `Zeroizing<[u8; 32]>` throughout)
- Vault header contents: confirm no derived key material is serialised into the header
- Recovery phrase handling: confirm phrase is not logged, not stored persistently, and not included in any error messages or debug output
- Recovery slot AAD: confirm `vault_id_bytes` is included in the AAD for both `wrap_master_key_for_recovery` and `unwrap_master_key_from_recovery`
