## Detailed Findings and Recommended Fixes

### Key material copied into plain stack locals
- **Severity**: CRITICAL
- **Location**: `src-tauri/src/auth/ceremonies.rs` (multiple: 219, 389, 556-557, 711-712, 954-955, 1043-1044, 1175-1176), `src-tauri/src/crypto/types/mod.rs` (16-18, 51-53, 128-130, 156-158)
- **Problem**: Sensitive key bytes are copied by value into plain `[u8; 32]` locals and by-value constructors.
- **Evidence**: `*...expose()` into local arrays and `from_bytes([u8; 32])` production constructors.
- **Plan Context**: Auth/crypto key handling is implemented and in active use in Phase 2.4 flows; this is not deferred by roadmap.
- **Recommended Fix**: Remove production by-value key constructors and eliminate stack copies by passing protected/borrowed key material.
- **Proposed Solution**: Restrict by-value constructors to tests, use protected constructors (`SecretBox`/borrowed forms), and refactor ceremony call sites accordingly.
- **Risk if Unchanged**: Key material can persist in unprotected stack memory, increasing memory disclosure risk.

### SQLCipher key material interpolated into heap strings
- **Severity**: CRITICAL
- **Location**: `src-tauri/src/auth/ceremonies.rs:197-199, 207-212`
- **Problem**: SQLCipher keys are hex-encoded into `String` and passed via PRAGMA SQL text.
- **Evidence**: `format!("PRAGMA key ... {}", hex::encode(...))` and `format!("PRAGMA rekey ...")`.
- **Plan Context**: Conflicts with memory-protection intent in implemented auth ceremonies.
- **Recommended Fix**: Replace PRAGMA string interpolation keying with raw-byte SQLCipher key/rekey API path.
- **Proposed Solution**: Use rusqlite/sqlcipher FFI helpers to set/rekey with byte buffers and keep unsafe localized with explicit safety invariants.
- **Risk if Unchanged**: Key bytes may remain in heap allocations after use.

### Vault header validation does not enforce Argon2 policy floor
- **Severity**: MEDIUM (partially valid / context-dependent)
- **Location**: `src-tauri/src/storage/cloud/vault_header.rs:86-106`
- **Problem**: `validate()` checks structure/encoding but not minimum Argon2 parameters.
- **Evidence**: No checks for `memory_cost/time_cost/parallelism`; validator is used in active recovery flows (`auth/ceremonies.rs:911-913`, `1128-1130`).
- **Plan Context**: Phase 2.4 explicitly forward-declares a minimal validator; richer validation is documented as Phase 4.3 scope.
- **Recommended Fix**: Enforce Argon2 minimum policy for primary slot and each `bip39` recovery slot during validation.
- **Proposed Solution**: Add explicit checks and dedicated `VaultHeaderError` variants for policy violations, plus unit tests.
- **Risk if Unchanged**: Weak/downgraded Argon2 parameters can pass trust boundary validation.

### Ceremony result can be masked by staging cleanup failure
- **Severity**: HIGH
- **Location**: `src-tauri/src/auth/ceremonies.rs:431-441` and similar upload/remove sequences (`655-660`, `881-886`, `1095-1104`)
- **Problem**: A successful upload can still return error when `remove_if_exists` fails.
- **Evidence**: Cleanup uses `?` after upload path, potentially overriding operation outcome.
- **Plan Context**: Staging-file semantics are implemented in Phase 2.4 and should preserve correct success/failure semantics.

- **Proposed Solution**: Introduce shared upload+cleanup helper with best-effort cleanup and explicit upload-result precedence.
- **Risk if Unchanged**: False-negative failures and inconsistent state reporting.
