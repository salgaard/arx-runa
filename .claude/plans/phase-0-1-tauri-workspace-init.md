# Plan: Phase 0.1 — Tauri Workspace Initialisation

## Goal

Generate a compilable Tauri v2 + Leptos 0.8 project skeleton with `src-tauri/` as a workspace member of a root package+workspace manifest, so that `cargo build` succeeds on an empty scaffold.

## Context

**Current repo state** (verified 2026-04-12):

- Root `Cargo.toml` is a bare `[package]` (`arx-runa` v0.1.0, edition 2024, empty `[dependencies]`).
- `src/main.rs` contains a hello-world `fn main()`.
- `src/styles.css` exists (unreferenced).
- No `src-tauri/` directory, no `Trunk.toml`, no `index.html`, no `package.json`, no `tauri.conf.json`.
- `.github/workflows/continuous-integration.yml` already exists (runs on `ubuntu-latest`) — not touched in this sub-phase.
- `docs/`, `scripts/`, `.claude/`, `README.md`, `CLAUDE.md` are in place and must be preserved.

**Roadmap context**:

- **Phase 0** — Project Scaffolding. Depends on: nothing.
- **Sub-phase 0.1** — First of three (0.1 → 0.2 → 0.3, strict order). Depends on: nothing.
- **Sibling sub-phases** (NOT in this plan): 0.2 populates `src-tauri/Cargo.toml` deps + module skeleton; 0.3 adds Trunk/Tailwind pipeline.
- **Estimated scope**: ~15 files generated by the Tauri template, 2 files modified (`Cargo.toml` root, `src-tauri/Cargo.toml`), 1 file deleted (`src/main.rs` hello-world, overwritten by template).
- **No pending architectural decisions** map to Phase 0.1.

**Canonical contract** (from `design.md#contract-surface`):

- Root `Cargo.toml` = package+workspace manifest (frontend crate at `src/` + `src-tauri/` as workspace member).
- Build entrypoints: `cargo tauri dev`, `cargo tauri build`.
- Baseline invariant: `cargo fmt`, `cargo clippy -D warnings`, `cargo test`, `cargo build --release` must succeed. Sub-phase 0.1 only needs `cargo build` green; clippy/fmt/release gates are enforced at end of 0.2 and 0.3.

## Design Concerns / Open Questions

### 1. Root `[lib]` vs `[[bin]]` mismatch with CSR Leptos (NON-BLOCKING)

- **Concern**: Deliverable 2 of the sub-phase specifies the root `Cargo.toml` include `[lib] crate-type = ["cdylib", "rlib"]`. For a pure CSR Leptos app compiled by Trunk, the frontend crate is usually a binary target (`[[bin]] name = "arx-runa", path = "src/main.rs"`), not a `cdylib`. The `cdylib/rlib` pattern is an SSR/hydrate convention.
- **Source**: `0.1-tauri-workspace-init.md` lines 14–26.
- **Impact**: If we literally copy the `[lib]` block and the template instead scaffolds a binary, Trunk's `target = "index.html"` will fail to locate a WASM-producing crate and `cargo build` may error with `no bin target named ...`.
- **Classification**: Non-blocking.
- **Resolution**: Follow whatever target declaration `cargo create-tauri-app . --template leptos` produces. If the generated root has `[[bin]]`, keep it; if it has `[lib] crate-type = ["cdylib", "rlib"]`, keep that. Do not hand-author a target block that conflicts with the template. Record the actual choice in Assumptions below. The sub-phase text is advisory here; the Contract Surface only mandates "package+workspace manifest with `src-tauri/` as a member" — the exact target kind is unspecified.

### 2. Leptos 0.6 → 0.8 template code churn (NON-BLOCKING)

- **Concern**: Deliverable 4 says "immediately update the generated Leptos dependency to 0.8 before first compilation." The template generates 0.6-era component code (`src/app.rs`, `src/main.rs`). Leptos 0.8 introduced breaking changes (`view!` macro, signal APIs, `mount_to_body`, `Effect::new`). Bumping the dep without touching the code may leave Phase 0.1 uncompilable.
- **Source**: `0.1-tauri-workspace-init.md` line 29; `roadmap.md` line 119.
- **Impact**: `cargo build` fails, deliverable 7 cannot be met, plan stalls on a code-migration task the sub-phase did not scope.
- **Classification**: Non-blocking.
- **Resolution**: Permit minor edits to `src/main.rs` and `src/app.rs` to make them compile against Leptos 0.8 (e.g. adjust `mount_to_body`, imports, any deprecated macros). Keep the frontend minimal — a `"Hello Arx Runa"` component is enough for 0.1. Anything beyond trivial migration is a signal the template shifted substantially and should be escalated before guessing.

### 3. `cargo create-tauri-app .` on a non-empty directory (NON-BLOCKING)

- **Concern**: The repo root already contains `Cargo.toml`, `src/main.rs`, `src/styles.css`, `docs/`, `README.md`, `CLAUDE.md`, `.github/`, `.claude/`, `scripts/`, `target/`. `cargo create-tauri-app .` may refuse to write into a dir that already has a `Cargo.toml`, or may silently overwrite it.
- **Source**: `0.1-tauri-workspace-init.md` lines 12, 67–71.
- **Impact**: The tool may abort, or worse, quietly clobber `README.md` / `CLAUDE.md` / docs. Lost work risk.
- **Classification**: Non-blocking.
- **Resolution**: **Before** running the generator: (a) delete `Cargo.toml` and `Cargo.lock`; (b) delete `src/main.rs` and `src/styles.css`; (c) leave every other directory (`docs/`, `.claude/`, `.github/`, `scripts/`, `README.md`, `CLAUDE.md`, `target/`) untouched. Then run the generator. After generation, restore the root `Cargo.toml` per the sub-phase template (package+workspace manifest). If the generator still refuses, use `--force` or scaffold into a temp dir and copy `src-tauri/` + any new root files over.

### 4. `resolver = "3"` toolchain requirement (NON-BLOCKING)

- **Concern**: `resolver = "3"` in the workspace block requires Cargo ≥ 1.84 (stable). Edition 2024 already implies resolver 3, so the explicit declaration is redundant but harmless on new toolchains and breaks on old ones.
- **Source**: `0.1-tauri-workspace-init.md` line 17.
- **Impact**: On a Cargo < 1.84 toolchain, workspace resolution fails with `unknown resolver version`.
- **Classification**: Non-blocking.
- **Resolution**: Keep `resolver = "3"` as specified. Assumption: developer toolchain is Rust stable ≥ 1.85 (current stable as of 2026-04). If the build fails with a resolver error, drop to `resolver = "2"` — edition 2024 still defaults to 3 implicitly.

### 5. `tauri.conf.json` version field omitted from table (NON-BLOCKING)

- **Concern**: The Tauri Configuration table in `design.md#tauriconfjson-key-settings` lists `identifier`, `productName`, `version`, `frontendDist`, `devUrl`, `beforeDevCommand`, `beforeBuildCommand`. Deliverable 6 says "set key values using the table." Fine — no real gap, just confirming version defaults to `0.1.0`.
- **Source**: `design.md` lines 336–345, `0.1-tauri-workspace-init.md` line 31.
- **Impact**: None if read carefully.
- **Classification**: Non-blocking.
- **Resolution**: Set `version = "0.1.0"` explicitly per the table.

### 6. `src/styles.css` relic (NON-BLOCKING)

- **Concern**: `src/styles.css` exists but is not referenced by the sub-phase. Phase 0.3 introduces `input.css` at the repo root. Leaving `src/styles.css` in place creates a dead file; deleting it here is slightly out of scope.
- **Source**: repo state, `0.1-tauri-workspace-init.md`, `design.md#workspace-layout`.
- **Impact**: Low — dead file clutters the tree.
- **Classification**: Non-blocking.
- **Resolution**: Delete `src/styles.css` during the pre-generation cleanup in step 3 below. It is not referenced by the design's target layout (which places CSS at `input.css` in the repo root), and Phase 0.3 owns CSS wiring.

## Assumptions

Every assumption listed here is something the plan takes for granted but the sub-phase does not state. If any is wrong, the implementation is wrong — correct before handoff.

1. **Toolchain**: Rust stable ≥ 1.85 is installed locally. `cargo` can understand `edition = "2024"` and `resolver = "3"`. `cargo-tauri` ≥ 2.0 and `cargo-create-tauri-app` are installed (`cargo install create-tauri-app tauri-cli --locked`).
2. **Working directory**: All commands run from `C:\Users\chris\source\repos\arx-runa` (Windows, bash shell — use forward-slash paths).
3. **Template output shape**: `cargo create-tauri-app . --template leptos --identifier com.arxruna.app --app-name "Arx Runa" --manager cargo` generates at least: `src-tauri/{Cargo.toml, tauri.conf.json, capabilities/, icons/, build.rs, src/main.rs, src/lib.rs}` plus a root `index.html`, a root Leptos crate source, and possibly a `package.json`. Exact target kind (`[lib]` vs `[[bin]]`) at the root is template-dependent — adopt whatever it produces (see Concern 1).
4. **Root target declaration**: If the template emits a `[[bin]]` target, the final root `Cargo.toml` will use that. If it emits `[lib] crate-type = ["cdylib", "rlib"]`, the plan uses that. The sub-phase's explicit `[lib]` block is treated as illustrative, not prescriptive.
5. **Frontend Cargo.toml location**: Frontend dependencies live in the root `Cargo.toml` `[dependencies]` block (the root IS the frontend crate per `design.md#workspace-layout`). No separate `frontend/Cargo.toml`.
6. **Frontend deps scope in 0.1**: Deliverable 2 requires the Frontend dependencies table from `design.md#frontend-src--compiled-by-trunk` (leptos 0.8 csr, leptos_meta, leptos_router, console_error_panic_hook 0.1, console_log 1, log 0.4, serde-wasm-bindgen 0.6, gloo-timers 0.3). These all land in 0.1, not 0.2 — 0.2 populates `src-tauri/Cargo.toml` backend deps only.
7. **No CI changes**: `.github/workflows/continuous-integration.yml` is not touched in Phase 0.1. Any CI work is deferred; Phase 0.2/0.3 may add steps, but 0.1 only needs local `cargo build` to pass.
8. **`package.json` handling**: If the template generates a root `package.json` for Tailwind, leave it in place unmodified (Phase 0.3 owns it). If it does not, do not create one in 0.1.
9. **No `.gitignore` regressions**: The template may add `target/`, `dist/`, `node_modules/` ignores. Merge them into the existing `.gitignore` (if any) without dropping existing entries. Do not check in `target/` or `Cargo.lock` changes beyond what is intentional.
10. **`src-tauri/Cargo.toml` stays near-empty of deps in 0.1**: Only the edition bump (to `2024`) and whatever the template auto-generates (`tauri`, `tauri-build`, `serde`, `serde_json`). Phase 0.2 populates the rest.
11. **`tauri.conf.json` `beforeDevCommand` / `beforeBuildCommand`**: Set to `"trunk serve"` / `"trunk build"` per the design table even though Trunk itself is configured in 0.3. `trunk` must be installed before `cargo tauri dev` is run; in 0.1 only `cargo build` is required, so missing `trunk` is acceptable at the end of 0.1.

## Security Implications

### (a) Expected sensitive path set

**None anticipated.** Phase 0.1 does not touch `src-tauri/src/crypto/`, `src-tauri/src/auth/`, or `src-tauri/src/storage/`. Those directories do not exist yet (they are created in Phase 0.2 as empty `mod.rs` + `error.rs` placeholders). Phase 0.1 only touches:

- Root `Cargo.toml`, `Cargo.lock`
- `src/main.rs`, `src/app.rs` (Leptos frontend entry — no crypto)
- `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`
- Template-generated `src-tauri/src/main.rs`, `src-tauri/src/lib.rs` (default Tauri boilerplate)
- `src-tauri/capabilities/*`, `src-tauri/build.rs`, `src-tauri/icons/*`

### (b) Invoke security-reviewer agent? **NO**

**Rationale**: Independently verified (not mirrored from sub-phase self-assessment). No cryptographic code is introduced. No key handling. No data access. No network code. The Tauri default capability is intentionally permissive per design — `design.md#capabilities` explicitly defers capability tightening to Phase 6 with a release-gate enforcement mechanism. Reviewing permissive capabilities at this point is premature.

### (c) Reasons review is unnecessary

1. Module performs no cryptographic operations — no AEAD, no KDF, no nonce generation, no zeroization boundaries.
2. No secrets enter or leave the process.
3. No file I/O beyond Cargo-controlled build artefacts.
4. The permissive default Tauri capability is a known, documented dev scaffold (design.md#capabilities) with an enforcement gate planned in Phase 6.
5. The implementer cross-check `/implement-plan` performs at verify-time against the Expected sensitive path set (item a) will still fire if any sensitive path is unexpectedly touched — drift protection remains in place.
