## Validation Checkpoint

**Automated tests**:
```bash
cargo test crypto::types
cargo test crypto::hkdf
cargo test crypto::nonce
```
All tests must pass.

**Acceptance criteria**:
- `derive_vault_keys` is deterministic: identical input yields identical output
- `derive_vault_keys` produces distinct outputs for distinct input keys
- `derive_vault_keys` produces three mutually distinct keys from one input
- `generate_nonce` produces 1000 unique nonces with no repeats
- `ZeroizeOnDrop` is confirmed: memory is zeroed after key drop (verify via raw pointer read in test)
- `CryptoError` variants can be constructed and matched in `match` expressions

**Manual verification**: None required for this sub-phase.

## Implementation Notes

- `MasterKey` is not yet defined in Phase 1; accept `&[u8; 32]` as the internal parameter for `derive_vault_keys` and alias or wrap it until Phase 2 (authentication) provides the canonical type.
- HKDF salt is the fixed domain separator `b"arx-runa-v1"`. Per RFC 5869, a fixed salt provides domain separation even when IKM has sufficient entropy, preventing cross-application key confusion.
- The three HKDF info strings must be byte-distinct and purpose-labelled. Do not use numeric suffixes — use the exact strings from the design to ensure cross-platform reproducibility.
- `ZeroizeOnDrop` tests must read back the dropped memory via a raw pointer captured before the drop. Use `ManuallyDrop` to control timing.
- `WrappedFileKey` does not implement `ZeroizeOnDrop` — it is ciphertext, not a key material.
- All key types must **not** implement `Debug`, `Clone`, or `Copy` — accidental copies defeat zeroization.

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- HKDF info-string uniqueness (confirm three strings are byte-distinct)
- Zeroization coverage (all `Secret<T>` fields zeroed on drop, no copies escape)
- `MasterKey` zeroed immediately after derivation call
