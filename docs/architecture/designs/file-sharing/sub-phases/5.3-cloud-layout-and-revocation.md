## Deliverables

1. Blob copy function in `src-tauri/src/sharing/cloud.rs`: copy each chunk UUID from `vault/<uuid>.blob` to `shared/<file_share_id>/<uuid>.blob` using the path-based `CloudTransport` API (`download_blob` to a temporary local ciphertext file, then `upload_blob` to the shared destination path, then delete the temporary file)
2. `file_share_id` assignment: generate a UUID v4 at share creation time; this value is stored in the `shares` table and embedded in the share package's `cloud_endpoint.path_prefix` field; it is distinct from `share_id` (per-recipient)
3. `shares` table insert: after blobs are copied, insert a row with `share_id`, `file_id`, `contact_id`, `file_share_id`, `cloud_path` (`shared/<file_share_id>/`), `created_at`
4. Revocation by blob deletion: delete all blobs under `shared/<file_share_id>/` via `CloudTransport::delete_blob` for each UUID in the chunk list; set `revoked_at` timestamp in the `shares` table row
5. Optional re-encryption flow:
   - Generate a new `file_key` via CSPRNG
   - Re-encrypt all chunks under the new `file_key` using XChaCha20-Poly1305
   - Upload re-encrypted blobs under a new `file_share_id`
   - Issue new share packages to all remaining active recipients
   - Delete the old `shared/<old_file_share_id>/` folder
   - Update `nodes` table with the new `file_key_wrapped` and new chunk UUIDs
6. Single-recipient revocation: mark the target share as `revoked_at` in the `shares` table; if other active shares exist for the same `file_share_id`, do not delete the cloud blobs; optionally trigger re-encryption flow if stronger guarantee is required
7. `received_shares` blob fetching: use `cloud_endpoint` from the `received_shares` row to construct a `CloudEndpoint`; use `CloudTransport` (Rclone) to download each chunk UUID from `shared/<file_share_id>/`; decrypt with `file_key` (read from `received_shares.file_key`, stored at import time)
8. Test suite covering:
   - Blob copy to `shared/` produces the correct path structure (`shared/<file_share_id>/<uuid>.blob`) for each chunk UUID
   - `shares` table insert contains correct `file_share_id`, `cloud_path`, and NULL `revoked_at` after share creation
   - Revocation deletes all blobs under the file_share_id and sets `revoked_at` in the shares row
   - Re-encryption flow: new blobs appear under a new `file_share_id`; old blobs are deleted; remaining-recipient shares are updated
   - Single-recipient revocation when other shares exist: `revoked_at` is set for the target share; cloud blobs are not deleted
   - `received_shares` fetch and decrypt round-trip: download chunks via mocked `CloudTransport`, decrypt with `file_key`, verify content matches original

## Validation Checkpoint

**Automated tests**:
```bash
cargo test sharing::cloud
cargo test sharing::revocation
```
All tests must pass with no warnings.

**Manual verification**:
- Share a test file; verify blobs appear in the cloud bucket under `shared/<file_share_id>/` with UUID names
- Revoke the share; verify blobs are deleted from the cloud; verify `revoked_at` is set in the local `shares` table
- Import the revoked share package on a second instance; verify download fails (blobs not found)

**Acceptance criteria**:
- Blob copy uses `CloudTransport` with temporary local ciphertext files only; no plaintext chunks are written to the filesystem during the copy
- Revocation deletes every blob listed in `chunk_uuids`; partial deletion (network failure mid-revocation) must leave the system in a state that can be retried
- `file_share_id` and `share_id` are never confused in any storage or API call
- Re-encryption flow produces blobs encrypted with a genuinely new `file_key` (verified by attempting to decrypt with the old `file_key`, which must fail)

## Implementation Notes

- `CloudTransport` is path-based, so blob copy uses temporary local ciphertext files (`download_blob(remote, temp_path)` then `upload_blob(temp_path, remote)`). Temporary files are deleted after successful upload, and no plaintext is ever materialized.
- Revocation is not atomic at the cloud level; implement as a sequential delete loop and record each deleted UUID to enable retry on partial failure (store progress in a transient in-memory list; no new table required)
- The `received_shares` fetch uses the `cloud_endpoint` JSON stored at import time; if the owner changes their cloud provider after sharing, old share packages still reference the original endpoint — this is an accepted limitation of the snapshot model
- Re-encryption is an owner-initiated operation, not automatic; the UI should present it as an option after single-recipient revocation when multiple recipients share the same `file_share_id`
- `MockTransport` from Phase 4.1 is sufficient for all automated tests in this sub-phase; no real cloud provider is needed for the test suite

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- Revocation correctness: all chunk UUIDs are deleted; no blob is silently skipped on error
- Public blob exposure: confirm threat model statement (design lines 349-355) is accurate for the implemented layout; blobs in `shared/` must be AEAD ciphertext only, never plaintext
- Re-encryption flow: new `file_key` is generated via CSPRNG; old `file_key` is zeroized after re-encryption; old blobs are deleted
