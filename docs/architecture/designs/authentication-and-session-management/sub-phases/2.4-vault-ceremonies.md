**Parent roadmap**: [roadmap.md](roadmap.md)

**Depends on**: [Phase 2.3](2.3-session-lifecycle-and-timeout.md) (`SessionManager`), Phase 3.1 (SQLCipher schema — cross-phase dependency for vault creation table structure), Phase 4 (cloud transport for vault header upload and manifest backup)

## Deliverables

1. **Vault creation** (`create_vault` in `src-tauri/src/auth/ceremonies.rs`) — 21-step ceremony:
   - Generate 32-byte key file via CSPRNG; write to user-chosen USB path
   - Compute `key_file_blake3 = blake3::hash(key_file_content)`
   - Generate 32-byte salt via CSPRNG; generate `vault_id` (UUID v4)
   - Argon2id + HKDF → `key_encryption_key`, `sqlcipher_key`, `manifest_key`; zeroize `master_key`
   - Create SQLCipher DB with `sqlcipher_key`; apply Phase 3.1 schema
   - Generate X25519 identity keypair; wrap X25519 private key with `key_encryption_key`; store in SQLCipher
   - Write vault header JSON to local staging and upload via `CloudTransport`
   - Begin session: store `SessionKeys` in `SessionManager`
2. **Password change** (`change_password` in `src-tauri/src/auth/ceremonies.rs`):
   - Authenticate with current credentials → acquire current `SessionKeys`
   - Accept new password; require USB key file to be present
   - Generate new salt (mandatory); Argon2id + HKDF → new keys; zeroize new `master_key`
   - Re-wrap all `file_key` values: decrypt with old `key_encryption_key`, encrypt with new `key_encryption_key`
   - Re-wrap X25519 private key: decrypt with old, encrypt with new `key_encryption_key`
   - Re-key SQLCipher: `PRAGMA rekey = '<new_sqlcipher_key>'`
   - Update vault header (new salt, same `key_file_blake3`); upload to cloud
   - Replace `SessionKeys` with new derived keys; zero old keys
3. **USB key file rotation** (`rotate_key_file` in `src-tauri/src/auth/ceremonies.rs`):
   - Authenticate with current credentials (requires old key file to be present)
   - Generate new 32-byte key file; write to new USB location
   - Generate new salt (mandatory); Argon2id + HKDF → new keys; zeroize new `master_key`
   - Re-wrap all `file_key` values and X25519 private key (same steps as password change)
   - Re-key SQLCipher; update vault header (new salt, new `key_file_blake3`); upload to cloud
   - Replace `SessionKeys`; zero old keys
4. **New-device recovery** (`recover_vault` in `src-tauri/src/auth/ceremonies.rs`):
   - Accept Rclone remote configuration
   - Fetch vault header from cloud; parse salt, argon2_params, `key_file_blake3`
   - Accept USB key file (auto-detection or manual selection)
   - Accept password; Argon2id + HKDF → session keys; zeroize `master_key`
   - Fetch encrypted manifest backup from cloud; decrypt with `manifest_key`
   - Import manifest into local SQLCipher (keyed with `sqlcipher_key`)
   - Begin session
5. Critical invariant enforced in all flows: `master_key` must not be assigned to a struct field, returned, or passed to a function that might store it — it lives only between Argon2id output and HKDF completion
6. Key property documented in code: encrypted cloud blobs are never touched during password change or key file rotation — only key wrapping changes (no chunk re-encryption)
7. Sharing relationships survive rotation: X25519 keypair is re-wrapped, not regenerated; assertion in tests confirms public key is identical before and after rotation
8. Tests:
   - Vault creation produces a vault header JSON with correct fields; SQLCipher DB opens with derived `sqlcipher_key`
   - Password change: old `key_encryption_key` cannot unwrap file_keys after change; new `key_encryption_key` can
   - Password change: SQLCipher DB opens with new `sqlcipher_key` and not with old `sqlcipher_key`
   - Key file rotation: X25519 public key is identical before and after rotation
   - Key file rotation: old `key_file_blake3` in vault header differs from new `key_file_blake3`
   - New-device recovery: reconstructs operational vault from cloud vault header + manifest backup
   - All flows: `master_key` does not appear in any struct after the derivation step (inspected via field enumeration in tests)

## Validation Checkpoint

**Automated tests**:
```bash
cargo test auth::vault
```
All tests must pass.

**Manual verification**:
- Full vault creation on a real machine with a USB drive present; confirm key file written to USB, vault header uploaded to cloud, session active
- Password change: confirm old credentials rejected and new credentials accepted after change
- New-device recovery: on a second machine, configure Rclone remote, insert USB key file, enter password; confirm vault is fully operational

**Security check** (before marking complete):
- Confirm no test or production path stores `master_key` in a named field or returns it from `create_vault` / `change_password` / `rotate_key_file`
- Confirm vault header JSON does not contain `key_encryption_key`, `sqlcipher_key`, or `manifest_key` — only `argon2_salt`, `argon2_params`, `key_file_blake3`, `vault_id`, `schema_version`

**Acceptance criteria**:
- All four ceremony functions produce correct results verified by automated tests
- `master_key` lifetime is bounded in all flows
- Password change and key file rotation leave cloud blobs unchanged (no re-upload of encrypted chunks)
- X25519 public key is preserved across key file rotation

## Implementation Notes

- `create_vault` should validate that the target USB path exists and is writable before generating key material — avoid generating a key file that cannot be written
- Vault header JSON schema: `{ "vault_id": "<uuid>", "schema_version": 1, "tier": 1|2, "argon2_salt": "<base64>", "argon2_params": { "memory_cost": 19456, "time_cost": 2, "parallelism": 1 }, "key_file_blake3": "<hex>"|null }` — no derived key material
- The re-wrapping loop in `change_password` and `rotate_key_file` operates on every `file_key` row in the SQLCipher `chunks` table — ensure it runs inside a transaction so partial failure does not corrupt key state
- `PRAGMA rekey` must be issued while the DB connection is open with the old key, before the old `sqlcipher_key` is zeroed
- In `recover_vault`, the manifest backup is decrypted entirely in memory before importing to SQLCipher (same exception as Phase 4.4 — typical manifest size < 10 MiB)
- Cross-phase dependency: if Phase 3.1 is not yet complete when Phase 2.4 is implemented, use a minimal stub schema (`CREATE TABLE _phase_stub (id INTEGER PRIMARY KEY)`) to allow the vault creation flow to be tested end-to-end; replace with the real schema once Phase 3.1 is merged

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- Ceremony correctness: all four flows zeroize `master_key` on every code path including error returns
- Re-wrapping logic: confirm old key material is zeroed after re-wrapping completes; confirm the re-key transaction is atomic
- `master_key` lifetime: confirm no compiler optimisation can hoist the `master_key` variable beyond its intended scope (use `Zeroizing<[u8; 32]>` throughout)
- Vault header contents: confirm no derived key material is serialised into the header
