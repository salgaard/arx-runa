Generate, update, or list Mermaid diagrams saved to `docs/architecture/diagrams/`.

## Arguments

- `<topic>` → generate a new diagram for the given component or flow
- `list` → show all diagrams in docs/architecture/diagrams/ with their types
- `update <filename>` → regenerate an existing diagram from current code state

---

## Generating a diagram

### Step 1 — Determine the diagram type

Select the Mermaid diagram type based on what is being visualised:

| Topic | Mermaid type | Direction |
|-------|-------------|-----------|
| Architecture overview, module structure | `flowchart` | `TD` |
| Key derivation tree, data pipelines | `flowchart` | `TD` |
| Authentication, encryption, sync flows | `sequenceDiagram` | — |
| Session lifecycle, vault states | `stateDiagram-v2` | — |
| SQLCipher schema (nodes, chunks, manifest_meta) | `erDiagram` | — |
| Rust structs, traits, type relationships | `classDiagram` | — |

### Step 2 — Gather context

Read the relevant sources before generating:
- `CLAUDE.md` — architecture decisions, module layout, naming conventions
- `.claude/memory/MEMORY.md` — architecture decisions already made
- Source files if they exist (e.g. `src-tauri/src/crypto/`, `src-tauri/src/auth/`)
- Existing diagrams in `docs/architecture/diagrams/` to avoid duplication

### Step 3 — Generate the Mermaid diagram

**Structural rules — prevents broken diagrams:**

- **Intermediate nodes must be explicit.** If a value fans out to multiple
  destinations (e.g. `master_key` → 3 HKDF calls), create a named node for it.
  NEVER use an edge label as a substitute for a node — this causes Mermaid to
  render duplicate phantom nodes, one per edge. Wrong: `A -->|"key"| B` and
  `A -->|"key"| C`. Right: `A --> KEY[key]`, then `KEY --> B` and `KEY --> C`.
- **Trace every node and edge before saving.** Walk through the diagram mentally:
  does each node appear exactly once? Does each edge connect the correct pair?
  Does the rendered fan-out match the intended data flow?

**Rendering quality rules — follow these strictly:**

- Node labels: max 4 words. Use a legend or description section for full names
- Subgraphs: group related nodes (e.g. `subgraph Crypto Layer`)
- Max 15 nodes per diagram — split into multiple diagrams if larger
- Direction: `TD` for trees/hierarchies, `LR` for horizontal pipelines
- Arrow labels: always label edges meaningfully (e.g. `-->|derives|` not just `-->`)
- For `sequenceDiagram`: use `activate`/`deactivate` to show scope
- For `erDiagram`: include cardinality and relationship labels
- For `classDiagram`: show only public interface, not internal implementation details
- No raw IDs as labels — always use human-readable names

**Splitting guidance — when a diagram exceeds 15 nodes:**

- Split on **trust boundaries** (client vs cloud, encrypted vs plaintext)
- Split on **layer boundaries** (auth layer, crypto layer, storage layer, UI layer)
- Never split in the middle of a flow — each diagram must be self-contained
- Create a parent "overview" diagram that references the child diagrams

**Styling with `classDef` — use for visual clarity:**

```mermaid
classDef secret fill:#dc2626,stroke:#991b1b,color:#fff
classDef crypto fill:#2563eb,stroke:#1e40af,color:#fff
classDef storage fill:#16a34a,stroke:#166534,color:#fff
classDef user fill:#9333ea,stroke:#6b21a8,color:#fff
classDef boundary fill:#f59e0b,stroke:#d97706,color:#000
```

Apply styles to categorise nodes:
- `secret` (red) — key material, passwords, plaintext data
- `crypto` (blue) — encryption/decryption operations, KDF, HKDF
- `storage` (green) — SQLCipher, blob storage, rclone
- `user` (purple) — user-facing: UI, IPC commands, inputs
- `boundary` (amber) — trust boundaries, security perimeters

Apply with `:::secret` after a node definition, e.g. `MK["master_key"]:::secret`

### Step 4 — Write the diagram file

Save to `docs/architecture/diagrams/<kebab-name>.md`.

File structure:

```
# <Diagram Title>

> Auto-generated by `/diagram`. Regenerate with `/diagram update <filename>`.
> Last updated: <ISO timestamp> (commit: <short hash>)

```mermaid
<diagram code>
```

## Description

<1–3 sentences: what this diagram shows and why it matters>

## Related

- Report log: <!-- link to relevant docs/report-log/ entry if one exists -->
- Source files: <!-- relevant src-tauri/src/ paths -->
```

### Step 5 — Update INDEX.md

Append one row to `docs/architecture/diagrams/INDEX.md`:

```
| [Title](filename.md) | <type> | `filename.md` | `src-tauri/src/<module>/` |
```

If regenerating (`update`), overwrite the existing file and update the timestamp row in INDEX.md.

### Step 6 — Confirm briefly

Output one line: `Generated diagram: <title>`

---

## Listing diagrams (`/diagram list`)

1. Read all `.md` files in `docs/architecture/diagrams/` (exclude `INDEX.md`)
2. Extract title, type, and related module from each file
3. Display as a table grouped by type

---

## Updating a diagram (`/diagram update <filename>`)

1. Read the existing diagram file at `docs/architecture/diagrams/<filename>`
2. Re-read the relevant source files to pick up any changes since last generation
3. Regenerate the Mermaid block while keeping the Description and Related sections
4. Update the timestamp and commit hash in the header
5. Overwrite the file — do not create a duplicate

---

## Exporting for the report

Mermaid diagrams in markdown are source files — for the bachelor report PDF,
they must be rendered to SVG or PNG.

**Using the Mermaid CLI (`mmdc`):**

```bash
# Install once
npm install -g @mermaid-js/mermaid-cli

# Export a single diagram (extract the mermaid block from the .md file first)
mmdc -i diagram.mmd -o diagram.svg -t neutral -b transparent

# Recommended settings for report figures:
# -t neutral    → clean greyscale-friendly theme
# -b transparent → no white background, blends with report
# -w 1200       → width in pixels (for PNG)
# -s 2          → scale factor for crisp PNG output
```

When preparing diagrams for the report:
- Use the `neutral` theme for print-friendliness (colours still work but are muted)
- Export as SVG when possible — scales without pixelation
- Every figure in the report MUST have a figure caption and be referenced in body text
  (per bachelor guidelines section 8.2)
