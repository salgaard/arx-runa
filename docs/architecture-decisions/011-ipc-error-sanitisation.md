# Decision-011: IPC Error Sanitisation and Redaction

**Date**: 2026-04-23  
**Status**: Accepted  
**Reviewed in**: Phase 6.1–6.5 implementation and audit

---

## Context

Arx Runa exposes encrypted data and authentication operations through Tauri IPC commands to the frontend. Error messages generated by the backend contain sensitive information:

- Full filesystem paths (`C:\Users\chris\Vault\...`)
- Cryptographic operation details (key derivation params, nonce values)
- Stack traces with internal module names
- Specific crypto failures that hint at attack vectors

The frontend must display errors to users, but **cannot safely display this information**. Transmitting raw errors over IPC violates the zero-knowledge and zero-trace threat models:

1. **Frontend storage risk**: If error messages are logged to console or stored temporarily, they persist as evidence on disk.
2. **Observability risk**: Error patterns could leak vault structure or key-derivation logic to observers.
3. **User-safety risk**: Generic-looking errors increase usability friction without security benefit; users need to know *why* an operation failed (auth, file not found, network issue) but not *how*.

Without a systematic redaction boundary, error handling would require defensive programming at each call site. This decision establishes **where and how** error sanitisation happens:

- **Frontend consumers (IPC handlers)** receive `IpcError` — safe, user-friendly variants only
- **Logging** carries full diagnostic detail server-side (`tracing::error!`), never sent to client
- **Error mapping** is explicit via `From<DomainError>` traits to prevent accidental leakage

---

## Decision

### 1. IPC Error Boundary

All command handlers return `Result<T, IpcError>`. The `IpcError` enum exposes only safe, generic error types with no internal detail:

```rust
/// Errors returned to the frontend. User-safe messages only.
#[derive(Debug, Serialize)]
#[serde(tag = "kind", content = "message")]
pub enum IpcError {
    VaultLocked(String),
    AuthenticationFailed(String),
    NotFound(String),
    AlreadyExists(String),
    CloudError(String),
    InvalidInput(String),
    InternalError(String),
}
```

Each variant carries a **single short message** suitable for UI display. No composite errors, no error chains.

### 2. Mapping Strategy: Domain Error → IpcError

Every domain error type (`AuthenticationError`, `StorageError`, `SyncError`, `SharingError`) implements `From<DomainError> for IpcError`. The mapping follows these rules:

1. **Log the raw error** for debugging: `tracing::error!("Auth error: {:?}", err);`
2. **Match on the variant** to classify severity (auth failure, not-found, network, internal)
3. **Return a generic message** matching the variant

**Example: `AuthenticationError`**

| Domain Variant | IPC Result |
|---|---|
| `InvalidCredentials` | `IpcError::AuthenticationFailed("Invalid credentials")` |
| `KeyFileNotFound` | `IpcError::AuthenticationFailed("Key file not found")` |
| `MemoryLockFailed(msg)` | Log `msg` server-side; return `IpcError::InternalError("Cannot lock memory for session keys")` |
| `VaultHeaderInvalid` | `IpcError::InternalError("Vault configuration error")` |

**Rationale for grouping**: `InvalidCredentials` and `KeyFileNotFound` both map to `AuthenticationFailed` because revealing which one failed is a security risk — an attacker can use this to brute-force existence of key files.

**Example: `StorageError`**

| Domain Variant | IPC Result |
|---|---|
| `NotFound` | `IpcError::NotFound(...)` |
| `ChecksumMismatch` | Log diagnostic; return `IpcError::InternalError("Data integrity error")` |
| `WrongKey` | Log diagnostic; return `IpcError::InternalError("Vault database key mismatch")` |
| `ConstraintViolation` | `IpcError::AlreadyExists(...)` |
| `Database(error)` | Log `error`; return `IpcError::InternalError("Database error")` |
| `Io(error)` | Log `error`; return `IpcError::InternalError("File operation failed")` |

### 3. Command Handler Pattern

All command handlers follow this structure:

```rust
#[tauri::command]
async fn example_command(
    input: String,
    state: tauri::State<'_, AppState>,
) -> Result<ExampleResponse, IpcError> {
    // 1. Validate input (user-provided, may emit InvalidInput)
    validate_vault_relative_path(&input)?;
    
    // 2. Call domain logic (may emit auth, storage, sync errors)
    let result = domain::perform_operation(&input).await?;
    
    // 3. Return IPC response (if no error, no sanitisation needed)
    Ok(ExampleResponse { success: true })
}
```

Domain errors bubble up via `?` operator; the `From` trait converts them to `IpcError` automatically.

### 4. Logging Rules

- **Server-side logs (tracing)**: Capture full diagnostic detail. Development can inspect `RUST_LOG=debug` output.
- **Client-side (frontend console)**: Never log error details beyond the sanitised `IpcError.message`.
- **Persistent state**: No error messages written to localStorage, sessionStorage, or IndexedDB.

### 5. Exceptions and Annotations

**Password-bearing IPC payloads**: Request payloads containing passwords are scrubbed immediately:

```rust
#[tauri::command]
async fn authenticate(
    password: String,  // User input, sensitive
    ...
) -> Result<AuthResponse, IpcError> {
    let password_bytes: Zeroizing<Vec<u8>> = password.into_bytes().into();
    let _ = std::mem::take(&mut password); // Scrub the original String
    // ... use password_bytes
}
```

Frontend must zeroize password UI state before clearing and never store it.

**Public/derivative data**: Path names selected *by the user* in success responses (e.g., "File saved to `Desktop/data.enc`") are not sanitised — they are user-provided and already visible in the UI.

---

## Consequences

### Benefits

1. **Zero-trace boundary**: Errors never carry key material, sensitive paths, or stack traces to the frontend.
2. **Logging completeness**: Full diagnostic info is available server-side for development and security audit.
3. **Consistent UX**: All commands follow the same redaction pattern; no surprises in error handling.
4. **Security by design**: Impossible to leak internal details by accident — the type system enforces it.

### Costs

1. **Developer friction**: On-call debugging requires `RUST_LOG=debug` console inspection, not frontend error messages.
2. **Generic errors**: Users see "Internal error" rather than "SQLCipher encountered a PRAGMA error" — this is intentional but reduces user agency for troubleshooting.
3. **Maintenance overhead**: Every new domain error requires an explicit `From` impl; forgetting it will not compile.

### Mitigations

- **Recommendation for UI**: Encourage users to check app logs (system event viewer on Windows, system logs on macOS, `journalctl` on Linux) when generic errors occur.
- **Versioning**: If error variants change, update the `From` impls in sync — never silently map to a catch-all.
- **Testing**: Error-sanitisation tests verify that each domain variant is covered. See `src-tauri/src/ui/security_audit.rs`.

## Decisions Made During Implementation (Phase 6.1–6.5)

| Item | Outcome |
|------|---------|
| **StorageError variant set** | Canonical set is `Database`, `NotFound`, `ChecksumMismatch`, `Io`, `WrongKey`, `ConstraintViolation`. Design §Error Sanitisation code block was illustrative (updated during Phase 6.1 review). |
| **Sharing error isolation** | `SharingError::AuthenticationFailed` never exposes HPKE/KEM detail (RFC 9180 decap failure, CTX mismatch, stream decrypt). Maps to `IpcError::AuthenticationFailed` with fixed message. |
| **Cloud transport failures** | `CloudTransportError::RcloneProcessFailed` logs stderr (scrubbed of secrets) server-side; IPC maps to generic `CloudError`. |
| **Input validation precedence** | Validate *all* request inputs before any domain logic — emit `InvalidInput` before auth/storage errors to distinguish user mistake from internal failure. |
