## Deliverables

1. Argon2id wrapper function in `src-tauri/src/auth/kdf.rs`: accepts `password: &[u8]`, `key_file_bytes: Option<&[u8; 32]>`, `salt: &[u8; 32]`, and Argon2 params; constructs input as:
   - Tier 1: `argon2_input = password_utf8_bytes`
   - Tier 2: `argon2_input = password_utf8_bytes || key_file_bytes`

   Returns `Zeroizing<[u8; 32]>` as `master_key`. Parameters: m = 65536 KiB (64 MiB), t = 3, p = 4, output 32 bytes
2. Integration with Phase 1.1's `derive_vault_keys` function: pass `master_key` to HKDF expansion to produce `key_encryption_key`, `sqlcipher_key`, `manifest_key`
3. `SessionKeys` struct in `src-tauri/src/auth/session.rs`: fields `key_encryption_key: SecretBox<[u8; 32]>`, `sqlcipher_key: SecretBox<[u8; 32]>`, `manifest_key: SecretBox<[u8; 32]>`, derived with `#[derive(ZeroizeOnDrop)]`
4. Memory locking on `SessionKeys` construction: call `mlock` (Linux) or `VirtualLock` (Windows) on the backing memory of all three key fields. Hard failure if locking fails — return `MemoryLockFailed` with the platform-specific error message (see design for exact message strings)
5. `master_key` zeroized immediately after all three HKDF derivations complete — it must not be stored in a struct field, returned from the function, or passed beyond the derivation scope
6. `AuthenticationError` enum in `src-tauri/src/auth/error.rs`: `InvalidCredentials`, `KeyFileNotFound`, `MemoryLockFailed(String)`, `VaultHeaderInvalid`
7. `InvalidCredentials` is returned for wrong password and for wrong key file — the caller cannot distinguish which factor failed
8. Tests:
    - Tier 1: correct password, no key file (`None`) → `SessionKeys` produced successfully
    - Tier 2: correct password + correct key file → `SessionKeys` produced successfully
    - Wrong password (Tier 1) → `InvalidCredentials`
    - Wrong password (Tier 2) → `InvalidCredentials`
    - Wrong key file bytes (Tier 2) → `InvalidCredentials`
    - `mlock` failure → `MemoryLockFailed` (simulate by exhausting lock quota in test harness)
    - Same inputs produce identical `SessionKeys` (KDF is deterministic)
    - Different passwords produce different `key_encryption_key` values
    - Different key file bytes produce different `key_encryption_key` values (Tier 2)
    - Tier 1 and Tier 2 with identical passwords produce different `key_encryption_key` values
    - `master_key` does not appear in `SessionKeys` fields after derivation

## Validation Checkpoint

**Automated tests**:
```bash
cargo test auth::kdf
cargo test auth::session_keys
```
All tests must pass.

**Manual verification**:
- On Linux: after `SessionKeys` is constructed, inspect `/proc/<pid>/status`; `VmLck` must increase by at least 96 bytes (three 32-byte keys)
- On Windows: confirm `VirtualLock` is called without error via debug logging (disabled in release builds)

**Security check**:
- Confirm `master_key` is not a field of any struct and does not appear in any `return` statement in `kdf.rs`
- Confirm Argon2id params in the wrapper match the design values (m = 65536, t = 3, p = 4)

**Acceptance criteria**:
- KDF produces deterministic output (same inputs → same `SessionKeys`)
- `mlock`/`VirtualLock` is applied to all key buffers before any key material is written into them
- `master_key` lifetime is bounded to the derivation function's stack frame
- `AuthenticationError::InvalidCredentials` is indistinguishable between wrong password and wrong key file

## Implementation Notes

- Use the `argon2` crate (part of the `RustCrypto` ecosystem); configure via `Params::new(m_cost, t_cost, p_cost, Some(output_len))`
- Input construction is tier-dependent: for Tier 1 pass only `password_utf8_bytes`; for Tier 2 pass `password_utf8_bytes || key_file_bytes` as the `password` argument to Argon2id — no separate API is needed
- Tier 2 split point is deterministic at `total_length - 32`; no length-prefix is required because the key file is always exactly 32 bytes
- `SecretBox<[u8; 32]>` from the `secrecy` crate wraps the key buffer and prevents accidental `Debug` printing; `ZeroizeOnDrop` ensures zeroization on struct drop
- Platform-specific `mlock` calls should be in a small `platform` sub-module with `#[cfg(target_os = "linux")]` and `#[cfg(target_os = "windows")]` guards
- Do not gate `MemoryLockFailed` as a soft warning — the design explicitly requires hard failure; a security product that silently skips memory locking is not trustworthy

---

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- Argon2id parameter values match design (m = 65536, t = 3, p = 4) — RFC 9106 §4 recommended tier
- `mlock`/`VirtualLock` is applied before key material is written, not after
- `master_key` lifetime: confirm it cannot escape the derivation scope via any code path (including error paths)
- `InvalidCredentials` indistinguishability: confirm no timing side-channel distinguishes wrong-password from wrong-key-file paths
