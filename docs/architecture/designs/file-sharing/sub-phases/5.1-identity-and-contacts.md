# Phase 5.1: X25519 Identity and Contact Management

**Parent roadmap**: [roadmap.md](roadmap.md)

**Depends on**: Phase 1.3 (key wrapping — `wrap_file_key` pattern for X25519 private key), Phase 3.1 (SQLCipher schema with `contacts` table)

## Deliverables

1. X25519 keypair generation using the `x25519-dalek` crate on first run, in `src-tauri/src/sharing/identity.rs`
2. Private key storage: wrap the X25519 private key with `key_encryption_key` using the existing `wrap_file_key` pattern from Phase 1.3 and store in SQLCipher
3. Public key export: serialise the 32-byte X25519 public key as a small binary file; produce QR code data (base64-encoded public key bytes) suitable for display in the Leptos UI
4. Contact import: accept `display_name` (required), `email` (optional, display label only), and `public_key` (32-byte X25519 key) — insert into the `contacts` table in SQLCipher
5. Fingerprint display: compute the first 16 lowercase hex characters of SHA-256 of the X25519 public key and return as a string for UI display
6. `SharingStore` trait (or `MetadataStore` extension) in `src-tauri/src/sharing/store.rs` with methods: `get_own_public_key`, `insert_contact`, `get_contact`, `list_contacts`, `delete_contact`
7. Test suite covering:
   - Keypair generation produces a valid 32-byte X25519 public key and a 32-byte private key
   - Private key wrap → unwrap round-trip yields the original private key bytes
   - Public key export file contains exactly 32 bytes matching the generated public key
   - Contact insert → get round-trip preserves all fields (`display_name`, `email`, `public_key`)
   - Contact list returns all inserted contacts; delete removes the correct entry
   - Fingerprint computation matches expected format: 16 hex characters, lowercase, deterministic

---

## Validation Checkpoint

**Automated tests**:
```bash
cargo test sharing::identity
cargo test sharing::contacts
```
All tests must pass with no warnings.

**Manual verification**:
- Export own public key file; verify it is exactly 32 bytes
- Import own public key as a contact; verify fingerprint displayed matches manual SHA-256 computation

**Acceptance criteria**:
- Keypair is generated exactly once on first run; subsequent runs load the wrapped private key from SQLCipher
- Private key is never written to disk unwrapped
- Contact CRUD operations are consistent: insert → list → get → delete leaves the table in the expected state
- Fingerprint output is exactly 16 lowercase hex characters for any 32-byte public key input

## Implementation Notes

- Use `x25519_dalek::StaticSecret` for private key generation (`StaticSecret::random_from_rng(OsRng)`) and `x25519_dalek::PublicKey` for the corresponding public key
- Reuse `wrap_file_key` from Phase 1.3 directly — the X25519 private key is 32 bytes, exactly the same size as `file_key`; no adapter is needed
- SHA-256 for fingerprinting: use the `sha2` crate already present in `Cargo.toml` for HKDF-SHA256 work; do not add a new dependency
- The `email` field is a display label stored in the `contacts` table as nullable TEXT; Arx Runa never reads it for delivery
- QR code data: produce the raw bytes as a base64 string; the Leptos UI layer handles rendering (Phase 5 UI is out of scope for this sub-phase)
- `SharingStore` should be a new trait rather than extending `MetadataStore` to avoid coupling the storage module to sharing semantics; both can share the same SQLCipher connection

---

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- Private key is wrapped with `key_encryption_key` before storage; unwrapped value must be held in `zeroize::Zeroizing<[u8; 32]>` and dropped as soon as the ECDH operation (Phase 5.2) completes
- Fingerprint computation must use SHA-256 of the raw 32-byte public key, not any encoded or formatted representation
- No private key material must appear in log output, error messages, or panic messages
