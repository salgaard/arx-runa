**Parent roadmap**: [roadmap.md](roadmap.md)  
**Design sections**: [Canonical Command Surface (Normative)](../design.md#canonical-command-surface-normative), [Command Signatures](../design.md#command-signatures), [Destination Manager](../design.md#destination-manager), [Cloud File Browser](../design.md#cloud-file-browser), and [State Contexts](../design.md#state-contexts) of [design.md](../design.md)  
**Contract anchor**: [Contract Surface](../design.md#contract-surface) in the parent `design.md` is canonical for command/type contracts; keep this sub-phase focused on sync wiring and destination management UI.  
**Depends on**: [Phase 6.6](6.6-file-operations-ui.md) (file operations complete; `ProgressModal` reuse pattern established)

This phase wires the sync workflow into the UI and delivers the destination management page, completing the cloud-side operation surface for authenticated users.

---

## Deliverables

1. Sync button in `AppShell` header (between vault name and lock button): calls `sync_to_cloud { progress }` via `invoke_command` with an `IpcChannel`; progress streamed to `ProgressModal`; button is disabled while `SyncState.syncing == true`
2. `SyncProvider` (`src/state/sync_context.rs`) wired to actually call `sync_to_cloud` via `SyncActions::sync()` — replacing the current stub; `SyncActions::clear()` already exists and must remain
3. `get_sync_status` polling in `SyncProvider`: polls every 5 seconds (same cadence as `SessionProvider` polling `get_session_status`) to surface live `SyncState { syncing, last_synced_at, pending_changes, error }`
4. "Last synced: `<timestamp>`" display in `SessionStatusBar` (`src/layout.rs`): shows formatted relative timestamp when `SyncState.last_synced_at` is `Some`, "Never synced" otherwise
5. `/destinations` route added to the `Router` in `src/app.rs`
6. New file `src/destinations.rs` with:
   - `DestinationList` component: calls `list_destinations` on mount, renders one `DestinationItem` per entry
   - `DestinationItem` component: shows destination name, type, and a delete button that calls `delete_destination { id }` with a `Modal` confirmation then refreshes the list
   - `AddDestinationForm` component: destination name field, type selector (local path / rclone remote name), path/remote field; validates non-empty before submitting; calls `add_destination` via `invoke_command`
7. `AddDestinationRequest` and `DeleteDestinationRequest` structs in `src/ipc_types/requests.rs`
8. Navigation link to `/destinations` in `AppShell` (e.g. cloud icon button)
9. `SyncResult` and `DestinationEntry` response types re-exported from `src/ipc_types/` if not already present (mirroring `src-tauri/src/ui/types.rs`)
10. **MVP profile deferral** (registered at IPC but no UI surface in this sub-phase): `recover_from_cloud`, `migrate_vault`, `sync_backup` — document explicitly in a code comment at each call site that UI is deferred

## Validation Checkpoint

**Automated tests**:
```bash
trunk build
cargo test --workspace
```

- `sync_provider_clears_on_lock` test: verify `SyncState` fields reset to defaults when `SyncActions::clear()` is called
- `add_destination_form_validates_empty_name`: unit test for the client-side validation function

**Manual verification**:
- Click the sync button; verify `ProgressModal` opens and receives progress events
- Observe "Last synced: just now" (or formatted timestamp) in `SessionStatusBar` after a completed sync
- Navigate to `/destinations`; verify the list of configured destinations renders
- Add a new destination and verify it appears in the list without a full page reload
- Delete a destination and verify it disappears with a confirmation step

**Acceptance criteria**:
- `trunk build` completes without errors
- `SyncState.last_synced_at` is updated after a successful `sync_to_cloud` call
- Sync button is disabled while a sync is in progress (no double-submit)
- `SyncState` is cleared when the vault is locked (existing `clear()` contract)
- `recover_from_cloud`, `migrate_vault`, and `sync_backup` have no reachable UI entry point in this sub-phase

## Implementation Notes

- `SyncProvider` polling must register a cleanup handler (same pattern as `SessionProvider`) to cancel the `gloo-timers` interval when the component unmounts
- `DestinationList` should use a `LocalResource` (not a raw `Effect`) to fetch destinations on mount and after add/delete mutations — follow the `use_vault_actions` navigate pattern for mutation-triggered refreshes
- Timestamp formatting: use `js_sys::Date` for current time and format as a relative string ("5 minutes ago") without pulling in a date library; a simple seconds/minutes/hours bucketing function is sufficient
- The `AddDestinationForm` must never log destination credentials (rclone remote config strings) — treat the path/remote field as opaque and pass it straight to the backend

---

## Security Review

**Not required** — this sub-phase contains sync trigger and destination management UI only. Destination credentials are opaque strings passed to the backend; no crypto or key material is handled in the frontend. `SyncState` clearing on lock is an existing invariant from Phase 6.4.
