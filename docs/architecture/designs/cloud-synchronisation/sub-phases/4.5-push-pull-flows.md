## Deliverables

1. `push_vault` function in `src-tauri/src/storage/cloud/sync.rs`:
   - Read local `snapshot_counter` from `manifest_meta`
   - Download and decrypt current cloud manifest backup → read cloud `snapshot_counter`
   - Conflict check: `cloud > local` or `cloud < local` → abort with error; `cloud == local` → safe to push
   - Collect all blob names from chunks table with staging files (via SQLCipher-specific query helper in sync module; not via `MetadataStore` trait)
   - Shuffle blob list (Fisher-Yates) to randomize upload order
   - Upload in parallel via `tokio::JoinSet` with `max_concurrent = 4`
   - On success per blob: delete staging file
   - On any upload failure: record errors, stop issuing new tasks, drain in-flight
   - Increment `snapshot_counter` via `MetadataStore::increment_snapshot_counter()`
   - Set `manifest_meta.last_synced_at` to current Unix timestamp
   - Upload manifest backup
   - On manifest upload failure: roll back `snapshot_counter`, return error
   - Upload vault header (idempotent)

2. `pull_vault` function:
   - Download vault header
   - User authenticates → derive `manifest_key`
   - Download and decrypt manifest backup
   - Import manifest to local SQLCipher
   - Read all chunk rows → list of (blob_name, blake3_checksum) via SQLCipher-specific query helper in sync module
   - Filter to blobs not already present locally
   - Download in parallel via `tokio::JoinSet`
   - Verify BLAKE3 checksum after download
   - On mismatch: delete downloaded file, record error (do not abort)
   - Report all verification failures

3. Conflict detection tests (all scenarios from design)
4. `delete_vault_from_cloud` function for full cleanup
5. Error recovery tests (interrupted push, manifest upload failure)

## Validation Checkpoint

**Automated tests**:
```bash
cargo test storage::cloud::sync
```
Must pass with comprehensive conflict detection and error recovery tests.

**Manual verification**:
- Create vault, add files, push to real cloud provider
- Verify blobs appear in cloud with random UUID names
- Simulate conflict (`cloud > local`): modify cloud `snapshot_counter` manually → push fails with correct error
- Simulate stale-cloud conflict (`cloud < local`): restore an older cloud manifest backup while local counter is newer → push fails with correct error
- Pull on new device: verify full vault recovery works
- Delete vault: verify all cloud files removed

**Acceptance criteria**:
- Push flow completes successfully for first push and subsequent pushes
- Conflict detection prevents data loss when counters diverge (`cloud > local` and `cloud < local`)
- Pull flow correctly restores vault from cloud
- BLAKE3 verification catches corrupted blobs
- Upload order is randomized (temporal correlation broken)

## Implementation Notes

- Use `tokio::task::JoinSet` for concurrent uploads/downloads
- Shuffle algorithm: Fisher-Yates in-place shuffle on `Vec<String>`
- Global chunk/blob enumeration for push/pull is SQLCipher-specific (direct `chunks` table query in sync module); `MetadataStore` remains scoped to file-oriented operations
- `snapshot_counter` rollback on failure requires transaction or explicit revert
- BLAKE3 verification happens *before* decryption (faster, avoids wasting CPU)
- Delete failures are logged but don't fail local operations (best-effort cloud cleanup)
- Full vault deletion requires user confirmation in UI (Phase 6), but implement backend function here

## Implementation Decisions

- `SyncChunkRecord` was placed in `src-tauri/src/storage/types/sync_chunk_record.rs` (and consumed by both `sqlcipher.rs` and `cloud/sync.rs`) to avoid reverse coupling from foundational SQLCipher storage code into the cloud sync module.
- Upload/download drivers were implemented with bounded in-flight futures (`FuturesUnordered`) keyed by `SyncConfig.max_concurrent`; push stops scheduling new work after the first failure and drains in-flight work, while pull aggregates verification/transport failures across the full set.
- Existing local staging blobs are now checksum-verified before pull skips them; mismatches are deleted and re-queued for download so pull does not silently trust stale/corrupt local blobs.
- Production Fisher-Yates randomization uses `rand::rngs::SysRng` (rand 0.10 system CSPRNG) with rejection sampling to avoid modulo bias; deterministic seeded RNG remains test-only.
- `pending_deletions` queue drain remains deferred from this sub-phase per plan concern C-5; follow-up is required in a later sync-orchestration phase to wire durable cloud delete retries into the active push path.
