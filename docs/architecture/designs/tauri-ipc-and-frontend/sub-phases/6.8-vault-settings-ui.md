# Phase 6.8: Vault Settings UI

**Parent roadmap**: [roadmap.md](roadmap.md)  
**Design sections**: [Canonical Command Surface (Normative)](../design.md#canonical-command-surface-normative), [Command Signatures](../design.md#command-signatures), [Rust-side password zeroization at IPC boundary](../design.md#rust-side-password-zeroization-at-ipc-boundary), and [Zero-Trace Compliance](../design.md#zero-trace-compliance) of [design.md](../design.md)  
**Contract anchor**: [Contract Surface](../design.md#contract-surface) in the parent `design.md` is canonical for command/type contracts; keep this sub-phase focused on settings page wiring and password zeroization compliance.  
**Depends on**: [Phase 6.7](6.7-sync-destination-ui.md) (sync and destination surface complete)

This phase delivers the vault settings page, exposing three administrative operations — password change, key file rotation, and vault deletion — each guarded by confirmation flows.

---

## Deliverables

1. `/settings` route added to the `Router` in `src/app.rs`
2. New file `src/settings.rs` with a `SettingsPage` component rendering three cards:
   - **Change Password** card (always visible)
   - **Rotate Key File** card (Tier 2 only — hidden when `SessionState.tier == 1`)
   - **Delete Vault** card (always visible, styled with danger variant)
3. Gear icon navigation link to `/settings` in `AppShell` header
4. `ChangePasswordForm` component:
   - Three `<input type="password">` fields: current password, new password, confirm new password
   - Client-side validation: new == confirm before submitting; both non-empty
   - Calls `change_password { current_password, new_password }` via `invoke_command`
   - Both password strings zeroized immediately after the IPC call completes (success or failure) — same `Zeroize` drop pattern as `AuthenticateRequest` / `CreateVaultRequest`
   - On success: inline "Password changed" confirmation; form fields cleared
   - On error: inline `IpcError` message; fields not cleared (user may retry)
5. `ChangePasswordRequest` struct in `src/ipc_types/requests.rs` with `#[derive(Zeroize, ZeroizeOnDrop)]` on `current_password` and `new_password` fields
6. `RotateKeyFileForm` component (Tier 2 only):
   - "Choose new key file location" button → native save dialog (`src/dialog.rs`)
   - Calls `rotate_key_file { new_key_file_destination }` via `invoke_command` once a path is chosen
   - On success: inline "Key file rotated" confirmation
   - On error: inline `IpcError` message
7. `DeleteVaultForm` component:
   - Text input: "Type your vault name to confirm deletion"
   - Delete button enabled only when input matches `SessionState.vault_name` exactly (case-sensitive)
   - Calls `delete_vault { confirmation }` via `invoke_command`
   - On success: calls `session_actions.clear()`, `vault_actions.clear()`, `sync_actions.clear()` then navigates to `/` (login screen)
8. `vault_tier` field exposed in `SessionState` (add to `session_context.rs` and the `SessionStatus` IPC type if not already present) so `RotateKeyFileForm` can conditionally render
9. `DeleteVaultRequest` and `RotateKeyFileRequest` structs in `src/ipc_types/requests.rs`

## Validation Checkpoint

**Automated tests**:
```bash
trunk build
cargo test --workspace
```

- `change_password_form_rejects_mismatched` unit test: validates that client-side check blocks submission when new != confirm
- `delete_vault_button_requires_exact_name` unit test: verify enable/disable logic for the delete button
- `change_password_request_zeroizes` test: construct `ChangePasswordRequest`, drop it, verify fields are zeroed (host-target test using `zeroize` introspection)

**Manual verification**:
- Navigate to `/settings` via the gear icon; verify all three cards render
- On a Tier 1 vault: verify "Rotate Key File" card is not visible
- On a Tier 2 vault: verify "Rotate Key File" card is visible
- Submit change password with mismatched confirmation; verify inline error appears without IPC call
- Submit change password with correct fields; verify success message appears and form clears
- Attempt vault deletion with incorrect name; verify delete button remains disabled
- Type exact vault name; verify delete button enables; confirm deletion; verify navigation to login screen

**Acceptance criteria**:
- `trunk build` completes without errors
- Both password strings in `ChangePasswordRequest` are zeroized on drop (verified by the host-target test)
- Delete vault clears all three state contexts before navigating away
- `RotateKeyFileForm` is conditionally rendered based on `SessionState.tier` — never shown for Tier 1 vaults

## Implementation Notes

- `ChangePasswordRequest` must derive `Zeroize, ZeroizeOnDrop` — the `derive` feature of the `zeroize` crate is already enabled in `Cargo.toml` (added in the Phase 6.3/6.6 build-fix)
- Password fields in `ChangePasswordForm` must use local `RwSignal<String>` — never store in a context or a parent-scope signal; signals are cleared immediately after IPC call completes
- The Tier 2 conditional rendering must read from `SessionState` (not from a hardcoded tier stored in the component) so that it stays correct if the vault tier changes (e.g., after `rotate_key_file`)
- "Delete vault" must not navigate away until the IPC call returns `Ok(())`; if the call fails, stay on the settings page and surface the error

## Security Review

**Required** — `change_password` passes two password strings through the IPC boundary. Verify that:
- `ChangePasswordRequest` correctly derives `Zeroize, ZeroizeOnDrop` and both fields are zeroed after the call
- The frontend does not log, store in localStorage, or pass password strings to any signal that outlives the form component
- The backend `change_password` handler (`src-tauri/src/ui/auth_commands.rs`) converts both `String` arguments to `Zeroizing<Vec<u8>>` at the IPC entry point (cross-phase invariant #6)
