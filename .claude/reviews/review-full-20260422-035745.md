### 2. SEC-009: CRITICAL Operation Gate Race Condition Allows Key Leak

- **Severity**: 🔴 **CRITICAL**
- **Occurrences**: 1 (confirmed in security-reviewer-auth)
- **Confidence**: **HIGH** — race window quantified; interleaving confirmed
- **Disposition**: **ACTIONABLE_NOW**
- **Location**: `src-tauri/src/auth/operation_gate.rs` (lines 78–94)
- **Rule Refs**: AUTH-007 (operation atomicity requirement) | **Design Refs**: D-202 (state coherence)
- **Problem**:
  - Operation gate check-then-act is non-atomic: gate status fetched, then checked, then lock released
  - Between check and act, concurrent task can modify gate state; key leak ensues
  - Two-instruction window allows TOCTOU exploit to bypass operation authorization
- **Evidence**:
  - `load_gate_state()` → `if state.is_locked()` → `unlock_operation()` is not under single mutex
  - Security-reviewer-auth documented race with interleaving trace
  - Lock released before operation completes; concurrent mutation observed in 3 test runs
- **Plan Context**: Design anchor D-202 requires atomic state transitions; Phase 2.1 mandates refactor
- **Recommended Fix**: Acquire lock once, hold through entire check-then-act sequence; use `parking_lot::Mutex`
- **Proposed Solution**:
  - Refactor to single atomic block:
    ```rust
    let mut gate = OPERATION_GATE.lock();  // once
    if gate.is_locked() { gate.unlock(); }
    // hold lock until operation confirmed
    ```
  - Add `#[must_use]` to gate guard to prevent accidental drop
  - Test with Loom concurrency model
- **Blast Radius**: **SYSTEM** — affects all authenticated operations
- **Estimated Complexity**: **MEDIUM** (requires careful lock refactor; risk of deadlock if not done correctly)
- **Risk if Unchanged**: Unauthorized key access via concurrent task; complete authentication bypass

## Design Challenges and Decisions

### Design Challenge CSR-002: Auth Module Boundary Violation

**Challenged Constraint**: [D-101] Layered architecture — auth layer must depend only on crypto + storage, not network/transport.

**Current State**: Auth directly imports `CloudTransport` for operation submissions.

**Rationale for Challenge**: 
- Current design couples auth to cloud-specific transport; violates testability principle
- Local-first and offline scenarios cannot reuse auth module
- Complicates dependency injection and mock testing

**Proposed Update**:
- Define `trait TransportProvider { fn submit_operation(...) -> Result<OperationId>; }`
- Move CloudTransport to app-layer initialization
- Inject provider to auth module at startup
- Benefit: auth becomes transport-agnostic; testable in isolation

**Related Findings**: CSR-002, AF-005 (dependency abstraction)

**Status**: **Requires Decision** — Architecture team should approve trait-based DI approach before Phase 2.1 implementation.

---

### Design Challenge CSR-003: AppState Lock Ordering Invariant

**Challenged Constraint**: [D-202] State coherence — all multi-lock operations must follow global lock ordering.

**Current State**: No defined lock order; concurrent threads may acquire auth_lock → crypto_lock → storage_lock or any permutation.

**Rationale for Challenge**:
- Current design is fragile; deadlock risk grows with code complexity
- Lock order should be enforced at type level, not documentation level
- Future maintainers may unknowingly violate ordering

**Proposed Update**:
- Define explicit lock ordering enum (Auth=1, Crypto=2, Storage=3)
- Refactor all multi-lock acquisitions to follow order
- Add type-safe guard (`OrderedLockGuard<T>`) that enforces ordering at compile time
- Enable deadlock detector in CI/CD

**Related Findings**: CSR-003, AF-009

**Status**: **Requires Decision** — Recommend prioritizing for Phase 2.1.

---

### Design Challenge CSR-005: Auth→Storage Schema Coupling

**Challenged Constraint**: [D-101] Module boundary — auth must not depend on storage schema internals.

**Current State**: Auth directly accesses `storage::schema::User` fields (e.g., `user.password_hash`).

**Rationale for Challenge**:
- Schema changes force auth changes; violates separation of concerns
- Makes storage schema part of auth's public interface
- Complicates schema versioning and migrations

**Proposed Update**:
- Define auth-layer types (e.g., `AuthUser { id, password_hash }`)
- Create adapter functions in storage module: `fn user_to_auth(storage::User) -> AuthUser`
- Auth only references AuthUser; decouples from schema
- Benefits: schema migrations transparent to auth; better encapsulation

**Related Findings**: CSR-005, AF-007 (boundary integrity)

**Status**: **Requires Decision** — Recommend for Phase 2.1; impacts storage module refactor.

### Appendix F: Deduplication Criteria
