# VoidGate — Authentication and Session Management Design

> Status: Design complete. Implementation target: Phase 2.
> Last updated: 2026-03-29

---

## Goals

- Two-factor authentication: password + USB key file (physical hardware factor)
- Password alone cannot compromise data — the key file is a mandatory cryptographic input
- USB key file auto-detected when inserted — no manual file selection required after first setup
- Session keys held in memory-locked RAM, zeroed on timeout
- Vault creation generates all initial material: key file, salt, vault header, SQLCipher DB, X25519 identity keypair
- Password and key file rotation supported without re-encrypting cloud blobs

---

## USB Key File

### Format and generation

The key file is 32 bytes (256 bits) of random data generated by CSPRNG (`rand::thread_rng().fill_bytes`). It is not a device identifier, serial number, or derived value. The file has no internal structure — it is raw entropy.

VoidGate generates the key file during vault creation and writes it to a user-chosen location on a removable drive. The user may rename the file or move it to any location on the drive. VoidGate does not impose or check a filename.

### Auto-detection via BLAKE3 fingerprint

At vault creation, VoidGate computes `blake3::hash(key_file_content)` and stores the 32-byte hash in the vault header alongside the Argon2 salt. The vault header is public by design (stored as plaintext JSON in the cloud), so the key file hash must not leak the key file content. BLAKE3 is preimage-resistant — the hash is a verifier, not a secret.
<!-- CITE: BLAKE3 specification — preimage resistance property -->

**Auto-detection flow (login):**

1. VoidGate monitors for removable drive mount events via OS-native device notification APIs
2. When a drive is mounted, VoidGate scans it for files that are exactly 32 bytes. The 32-byte size filter makes scanning near-instant — almost no legitimate files are exactly 32 bytes
3. For each 32-byte file found, VoidGate computes `blake3::hash(content)` and compares to the hash stored in the vault header
4. If a match is found, the key file field in the login UI is auto-populated with the file path
5. The user still enters their password and explicitly confirms authentication — USB detection fills one field, it does not auto-authenticate

**Local path hint:** On the same machine, VoidGate stores the last-used key file path in a local config file (not SQLCipher, not the vault header). On subsequent logins, it checks the remembered path first before scanning the whole drive. If the file has moved, it falls back to full-drive scanning.

### Device monitoring

VoidGate uses OS-native device notification APIs for USB detection:

- **Windows**: `RegisterDeviceNotification` via the `windows` crate, listening for `DBT_DEVICEARRIVAL` events, or WMI `Win32_VolumeChangeEvent`
- **Linux**: `udev` crate, monitoring for block device add events with `SUBSYSTEM=block`

The device monitoring runs as a background task in the Rust backend. When a mount event fires, VoidGate enumerates files on the new volume.

**Trait boundary:**

```rust
/// Monitors for removable storage device mount and unmount events.
trait DeviceMonitor: Send + Sync {
    /// Returns a stream of device mount events.
    fn watch(&self) -> impl Stream<Item = DeviceEvent>;
}

enum DeviceEvent {
    Mounted { mount_path: PathBuf },
    Unmounted { mount_path: PathBuf },
}
```

Concrete implementations: `WindowsDeviceMonitor`, `LinuxDeviceMonitor`. A `MockDeviceMonitor` emits synthetic events for testing without hardware.

### Security analysis of key file hash in vault header

The vault header is stored in the cloud (plaintext JSON). An attacker who obtains the vault header learns the BLAKE3 hash of the key file. This allows:

- **Verification**: given a candidate file, the attacker can check if it matches. This is equivalent to trying the file with the KDF (which they can also do), so the hash provides no additional advantage.
- **No key recovery**: BLAKE3 is preimage-resistant. The hash cannot be reversed to obtain the 32-byte key file content.
- **No brute force acceleration**: the key file has 256 bits of entropy. Brute-forcing the hash is computationally infeasible.

**Threat model statement**: storing `blake3(key_file)` in the vault header does not weaken the authentication model. It provides the same information an attacker would gain by attempting authentication with candidate files.

## Input Construction for Argon2id

### Password and key file combination

The Argon2id "password" input is constructed as:

```
argon2_input = password_utf8_bytes || key_file_bytes
```

where `password_utf8_bytes` is the password encoded as UTF-8, and `key_file_bytes` is the raw 32-byte key file content.

Simple concatenation is unambiguous because the key file is always exactly 32 bytes. Given the combined input and its total length, the split point is deterministic at `total_length - 32`. Length-prefixing adds complexity for a non-existent ambiguity. Hashing the password before Argon2id would destroy the benefit of Argon2id's memory-hard processing of the raw password.

### Salt

The Argon2id salt is 32 bytes generated by CSPRNG at vault creation. It is stored in the vault header (plaintext, by design — salt is a public parameter needed before key derivation).

32 bytes exceeds the OWASP/NIST minimum of 16 bytes. The choice is consistent with the 256-bit key size used throughout VoidGate.
<!-- CITE: OWASP Password Storage Cheat Sheet — salt recommendations -->
<!-- CITE: NIST SP 800-132 — Recommendation for Password-Based Key Derivation -->

### Argon2id parameters

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Memory (m) | 19456 KiB (19 MiB) | OWASP minimum for Argon2id |
| Iterations (t) | 2 | OWASP minimum |
| Parallelism (p) | 1 | Single-threaded derivation |
| Output length | 32 bytes (256 bits) | Matches XChaCha20-Poly1305 key size |

These are minimums. The parameters are stored in the vault header, allowing future increases without breaking existing vaults. A vault created with higher parameters will use those parameters on all devices.

### Key derivation from master_key

After Argon2id produces `master_key`, HKDF-SHA256 derives three vault-level keys:

```
master_key (32 bytes, Argon2id output, held in mlocked memory)
    ├─ HKDF(info: "voidgate-key-encryption")  → key_encryption_key
    ├─ HKDF(info: "voidgate-sqlcipher")        → sqlcipher_key
    └─ HKDF(info: "voidgate-manifest-backup")  → manifest_key
```

`master_key` is zeroed immediately after all three HKDF derivations complete. It is never stored, never logged, and never leaves the derivation function's scope.

## Session Management

### SessionKeys struct

```rust
/// Holds all derived keys for the duration of an authenticated session.
/// All fields are mlocked and zeroed on drop.
#[derive(ZeroizeOnDrop)]
struct SessionKeys {
    key_encryption_key: Secret<[u8; 32]>,
    sqlcipher_key: Secret<[u8; 32]>,
    manifest_key: Secret<[u8; 32]>,
}
```

`SessionKeys` is the single owner of all sensitive key material during a session. It is allocated in mlocked memory and implements `ZeroizeOnDrop`.

### Memory locking

All key buffers are locked into physical RAM via `mlock` (Linux) / `VirtualLock` (Windows) to prevent the OS from swapping them to disk.

**Failure handling**: if `mlock`/`VirtualLock` fails, VoidGate refuses to create the session and returns a clear error message explaining the issue and how to fix it:

- Linux: "Cannot lock memory. Increase the memory lock limit: `ulimit -l unlimited` or edit `/etc/security/limits.conf`."
- Windows: "Cannot lock memory. Run VoidGate as administrator or adjust the 'Lock pages in memory' policy."

**Rationale**: a security product that silently degrades its memory protection is not trustworthy. Hard failure with a clear fix is preferable to silent degradation. The required memory is < 1 KiB (three 32-byte keys), well within default `RLIMIT_MEMLOCK` limits (typically 64 KiB+).

### Session lifecycle

```
[No session] ──authenticate()──► [Active session]
                                       │
                              timeout or manual lock
                                       │
                                       ▼
                              [Session expired]
                              (all keys zeroed)
                                       │
                              re-authenticate()
                                       │
                                       ▼
                              [Active session]
```

**State transitions:**

1. **No session → Active**: user provides password, USB key file is detected (or selected manually). Argon2id + HKDF derive `SessionKeys`. Keys are mlocked. SQLCipher DB is opened with `sqlcipher_key`.

2. **Active → Expired**: activity-based timeout fires (default: 15 minutes of inactivity). All keys in `SessionKeys` are zeroed via `zeroize()`. SQLCipher connection is closed. The struct is dropped. File operations in progress must complete or be cancelled before zeroing.

3. **Expired → Active**: user re-authenticates with password + USB key file. Full derivation runs again.

### Timeout mechanism

**Activity-based with configurable duration:**

- Default: 15 minutes of inactivity
- A timer resets on every Tauri IPC command invocation (file upload, download, browse, etc.)
- The timer runs as a `tokio` task. When it fires, it sends a signal to the session manager to zero keys
- If an operation is in progress when the timeout fires, the session manager waits for the current operation to complete, then zeroes keys. Operations are not aborted mid-stream to avoid partial writes.
- The timeout duration is stored in local config (not SQLCipher — must be readable before authentication)

**Timeout UX:**
- 60 seconds before timeout: frontend shows a warning
- On timeout: frontend shows the login screen. Any open file views are cleared from memory.

### Error handling

Authentication errors must not reveal which factor was wrong:

```rust
#[derive(thiserror::Error, Debug)]
pub enum AuthenticationError {
    #[error("authentication failed")]
    InvalidCredentials,

    #[error("key file not found on the device")]
    KeyFileNotFound,

    #[error("cannot lock memory for session keys")]
    MemoryLockFailed(String),

    #[error("vault header is missing or corrupt")]
    VaultHeaderInvalid,
}
```

`InvalidCredentials` is returned for wrong password, wrong key file, or wrong password + wrong key file — the caller cannot distinguish the cases. `KeyFileNotFound` is only returned when no 32-byte file matches the vault header's BLAKE3 hash — this does not reveal the password status.

## Vault Creation Flow

First-run sequence when the user creates a new vault:

```
1.  User sets password
2.  VoidGate prompts: "Insert a USB drive to store your key file"
3.  DeviceMonitor detects USB insertion → mount_path
4.  User confirms target drive (or picks a subdirectory)
5.  VoidGate generates 32-byte key file via CSPRNG
6.  Writes key file to chosen location on USB
7.  Computes key_file_blake3 = blake3::hash(key_file)
8.  Generates 32-byte salt via CSPRNG
9.  Generates vault_id (UUID v4)
10. Argon2id(password || key_file, salt, params) → master_key
11. HKDF(master_key, "voidgate-key-encryption")  → key_encryption_key
12. HKDF(master_key, "voidgate-sqlcipher")        → sqlcipher_key
13. HKDF(master_key, "voidgate-manifest-backup")  → manifest_key
14. zeroize(master_key)                            — master_key is gone
15. Create SQLCipher DB keyed with sqlcipher_key
16. Create schema: nodes, chunks, manifest_meta, contacts, shares, received_shares
17. Generate X25519 identity keypair
18. Wrap X25519 private key with key_encryption_key → store in SQLCipher
19. Write vault header JSON to local staging:
    {
      "vault_id": "<uuid>",
      "schema_version": 1,
      "argon2_salt": "<base64>",
      "argon2_params": { "m": 19456, "t": 2, "p": 1 },
      "key_file_blake3": "<hex>"
    }
20. Upload vault header to cloud via CloudTransport
21. Session begins: SessionKeys in mlocked memory
```

**Critical invariant**: `master_key` exists for exactly one scope — between step 10 and step 14. It must never be assigned to a field, returned, or passed to a function that might store it.

## Password Change Flow

1. Authenticate with current credentials → current `SessionKeys`
2. User enters new password
3. Read key file from USB (must be present during password change)
4. Generate new 32-byte salt via CSPRNG (reusing salt with a different password is a vulnerability — same password-salt pair must never be reused)
5. Argon2id(new_password || key_file, new_salt) → new_master_key
6. HKDF → new key_encryption_key, new sqlcipher_key, new manifest_key
7. zeroize(new_master_key)
8. Re-wrap all `file_key` values: decrypt with old `key_encryption_key`, encrypt with new `key_encryption_key`
9. Re-wrap X25519 private key: decrypt with old, encrypt with new `key_encryption_key`
10. Re-key SQLCipher DB: `PRAGMA rekey = '<new_sqlcipher_key>'`
11. Update vault header: new salt, same argon2_params (unless user requested upgrade), same key_file_blake3
12. Upload updated vault header + manifest backup to cloud
13. Zero old keys, replace `SessionKeys` with new derived keys

**Key property**: file_keys themselves do not change — only their wrapping changes. Encrypted blobs in the cloud are completely unaffected. No chunk re-encryption is needed.

## USB Key File Rotation

The key file is a cryptographic input, not a lookup key. Changing it requires re-derivation:

1. Authenticate with current credentials → current `SessionKeys`
2. User inserts new USB drive (or same drive with a new file)
3. VoidGate generates new 32-byte key file, writes to new location
4. Generate new salt (mandatory — salt must change when any KDF input changes)
5. Argon2id(password || new_key_file, new_salt) → new_master_key
6. HKDF → new key_encryption_key, new sqlcipher_key, new manifest_key
7. zeroize(new_master_key)
8. Re-wrap all file_keys and X25519 private key (same as password change, steps 8-9)
9. Re-key SQLCipher (step 10)
10. Update vault header: new salt, new key_file_blake3
11. Upload updated vault header + manifest backup
12. Zero old keys, replace `SessionKeys`

**Sharing relationships survive key file rotation.** The X25519 identity keypair is re-wrapped under the new `key_encryption_key`, but the keypair itself does not change. Contacts who have the user's X25519 public key can still create share packages for them. This is a correction from the initial sharing design document, which assumed key rotation would break sharing relationships.

**Requirement**: the old key file must be present (accessible) during the rotation ceremony. VoidGate needs the old key file to derive the old keys, unwrap file_keys and the X25519 private key, then re-wrap with the new keys.

## New-Device Recovery Flow

When a user sets up VoidGate on a new machine:

1. Configure Rclone remote (cloud backend connection)
2. Fetch vault header from cloud → obtain salt, argon2_params, key_file_blake3
3. Insert USB key file drive
4. VoidGate scans for 32-byte files, matches against key_file_blake3
5. User enters password
6. Argon2id(password || key_file, salt) → master_key → HKDF → session keys
7. Fetch encrypted manifest backup from cloud
8. Decrypt manifest with manifest_key
9. Import manifest into local SQLCipher (keyed with sqlcipher_key)
10. Session begins — vault is operational on the new device

## Trait Boundaries

### KeySource

```rust
/// Reads cryptographic key material from a storage medium.
trait KeySource: Send + Sync {
    /// Reads the key file and returns its contents.
    /// Returns an error if the file is not found, not readable,
    /// or not exactly 32 bytes.
    fn read_key(&self) -> Result<Zeroizing<[u8; 32]>, KeySourceError>;
}
```

Implementations:
- `FileKeySource` — reads from a filesystem path (production)
- `MockKeySource` — returns controlled bytes (testing)

### DeviceMonitor

```rust
/// Monitors for removable storage device mount and unmount events.

    /// Returns a stream of device mount events.
    fn watch(&self) -> impl Stream<Item = DeviceEvent>;

```

Implementations:
- `WindowsDeviceMonitor` — WMI or `RegisterDeviceNotification`
- `LinuxDeviceMonitor` — `udev` crate
- `MockDeviceMonitor` — emits synthetic events (testing)

## Open Decisions

| Decision | Options | Status |
|----------|---------|--------|
| Key file user-chosen filename during creation | Let user name the file vs. generate a random name | Minor UX decision, not blocking |
| Argon2id parameter upgrade policy | Allow increasing params on existing vaults vs. fixed at creation | Deferred; current design stores params in vault header |
| Session timeout during active upload | Wait for completion vs. cancel and clean up | Design says wait; needs verification during Phase 6 integration testing |

---

## Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Key file format | 32 bytes CSPRNG, no structure | Maximum entropy, no filename leakage |
| Key file identification | BLAKE3 hash in vault header | Preimage-resistant, enables auto-detection on new devices |
| USB detection | OS-native device events (WMI/udev) | Responsive, professional UX |
| Key file discovery | Scan 32-byte files, match BLAKE3 | No filename convention needed |
| Argon2id input | `password_utf8 \|\| key_file_bytes` | Unambiguous (fixed 32-byte suffix), preserves Argon2id password processing |
| Salt size | 32 bytes | Exceeds OWASP minimum, consistent with 256-bit theme |
| Session timeout | Activity-based, 15 min default, configurable | Balances security and usability |
| mlock failure | Hard fail with clear error | Security product must not silently degrade |
| Password change | Re-wrap keys, no chunk re-encryption | Per-file key model advantage |
| Key file rotation | Re-wrap keys, identity keypair preserved | Sharing relationships survive rotation |
