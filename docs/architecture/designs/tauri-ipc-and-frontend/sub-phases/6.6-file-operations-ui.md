# Phase 6.6: File Operations UI

**Parent roadmap**: [roadmap.md](roadmap.md)  
**Design sections**: [Canonical Command Surface (Normative)](../design.md#canonical-command-surface-normative), [Command Signatures](../design.md#command-signatures), [Vault Browser](../design.md#vault-browser), [In-App File Viewing (Zero-Trace)](../design.md#in-app-file-viewing-zero-trace), and [Zero-Trace Compliance](../design.md#zero-trace-compliance) of [design.md](../design.md)  
**Contract anchor**: [Contract Surface](../design.md#contract-surface) in the parent `design.md` is canonical for command/type contracts; keep this sub-phase focused on UI wiring and Zero-Trace properties.  
**Depends on**: [Phase 6.5](6.5-backend-command-wiring.md) (backend commands fully wired; download and delete return real results)

This phase adds download and delete actions to the vault browser's `FileItem` component, and implements the in-app file content viewer for MVP types — completing the read-side of the file operation surface.

---

## Deliverables

1. Download button on each `FileItem` (non-directory entries only): click opens a native save dialog (`src/dialog.rs`) to select a destination path, then calls `download_file { file_id, destination_path, progress }` via `invoke_command`; progress is streamed through an `IpcChannel` to a `ProgressModal`
2. `DownloadFileRequest` struct in `src/ipc_types/requests.rs` mirroring the `download_file` command signature (`file_id: String`, `destination_path: String`, `progress: JsValue` with `#[serde(skip)]`)
3. Delete button on each `FileItem` (non-directory entries only): click opens a `Modal` confirmation ("Delete `<name>`? This cannot be undone."); confirm calls `delete_file { file_id }` via `invoke_command`; on success calls `vault_actions.navigate(current_path)` to refresh the listing; on error surfaces the `IpcError` message inside the confirmation modal
4. Inline file preview triggered by clicking a file name (non-directory): checks `file.size_bytes <= 52_428_800` (50 MiB guard) and the file extension against the MVP supported-type list before calling `get_file_content { file_id }`
5. MVP supported preview types: plain text (`.txt`, `.md`, `.log`, `.csv`), images (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`); all other types show "No preview available — use download to view this file" without calling the command
6. `ContentViewerModal` component in `src/vault.rs`: full-screen `Modal` rendering text in a scrollable `<pre>` block or an `<img>` element depending on detected type; cleared from all signals when the modal is dismissed (Zero-Trace: no lingering bytes in reactive state)
7. `ProgressModal` reuse verified: download must use the same `ProgressModal` from `src/transfer.rs` as upload; remove any upload-specific hardcoding that would prevent reuse

## Validation Checkpoint

**Automated tests**:
```bash
trunk build
```

- `file_size_allows_preview` unit test: returns `false` for sizes > 52 428 800, `true` at exactly the limit
- `extension_is_previewable` unit test: covers all six supported extensions plus at least three unsupported ones

**Manual verification**:
- Right-click (or icon button) on a file entry; verify download button appears for files, not for directories
- Click download; verify native save dialog opens; confirm destination and verify `ProgressModal` appears and reaches 100%
- Click delete on a file; verify confirmation modal appears; confirm and verify the entry disappears from `FileList` without a full page reload
- Click a `.txt` file name; verify `ContentViewerModal` opens with scrollable text content
- Click a `.png` file name; verify image renders inside the modal
- Click an unsupported file type; verify "No preview available" message appears without a network call
- Click a file larger than 50 MiB (or mock the size); verify "File too large to preview" message appears

**Acceptance criteria**:
- `trunk build` completes without errors
- `ContentViewerModal` holds no signal state after dismissal (inspect with Leptos DevTools or a manual signal check in tests)
- Delete confirmation is required — no single-click deletion
- `ProgressModal` opens for downloads and reaches 100% on completion

## Implementation Notes

- Reuse `open_save_dialog` from `src/dialog.rs` (or add it alongside `open_file_dialog`) for the download destination picker
- `ContentViewerModal` must call `content_signal.set(None)` (or equivalent) in its `on_cleanup` / dismiss handler — not just hide the modal — so decrypted bytes are dropped from WASM memory
- Text preview: decode the `Vec<u8>` response as UTF-8; surface a "Could not decode file as UTF-8" message if decoding fails rather than panicking
- Image preview: construct a `Blob` from the bytes and a `URL.createObjectURL` to set as `<img src>`; revoke the object URL in `on_cleanup` to avoid memory leaks
- File type detection is extension-based only — do not fetch content to sniff type; the guard must run before `invoke_command` is called
