## Deliverables

1. `upload_manifest_backup` function in `src-tauri/src/storage/cloud/manifest_backup.rs`:
   - SQLCipher `VACUUM INTO '<temp_path>'` to export consistent snapshot
   - Load manifest export into buffer (explicit exception to streaming: manifests typically <10 MiB)
   - Generate 24-byte nonce via CSPRNG
   - Encrypt with XChaCha20-Poly1305 using `manifest_key` — see [Encryption scheme](../design.md#encryption-scheme) in `design.md` for AAD rationale and wire format
   - Write `[nonce | ciphertext | tag]` to temp file
   - Zeroize manifest buffer
   - `upload_blob(temp_file, "manifest/manifest-backup.blob")`
   - Delete temp files
2. `download_manifest_backup` function:
   - `download_blob("manifest/manifest-backup.blob", temp_path)`
   - Read blob, extract 24-byte nonce
   - Decrypt with `manifest_key`, no AAD
   - Write decrypted manifest to Arx Runa data directory as local SQLCipher DB
   - Zeroize manifest buffer
   - Open SQLCipher with `sqlcipher_key` to verify integrity
   - Delete temp file
3. Tests: Upload → download round-trip, verify encryption, test decryption failure with wrong key

## Validation Checkpoint

**Automated tests**:
```bash
cargo test storage::cloud::manifest_backup
```

**Manual verification**:
- Upload manifest backup to real cloud provider
- Verify `manifest/manifest-backup.blob` in cloud is encrypted (not plaintext SQLite)
- Download and decrypt — verify SQLCipher DB can be opened

**Acceptance criteria**:
- Manifest backup is encrypted before upload
- Decryption produces valid SQLCipher database
- Zeroization of manifest buffer occurs after use

## Implementation Notes

- Use `rusqlite::Connection::backup_to_path` or `VACUUM INTO` for export
- Loading entire manifest into memory is acceptable here (typical size <10 MiB)
- `manifest_key` derivation — see [Encryption scheme](../design.md#encryption-scheme) in `design.md` for the HKDF info string. Do not reproduce it here.
- Temp files in Arx Runa staging directory
- On decryption failure, return error — do not attempt to parse corrupted data

## Implementation Decisions

- `MANIFEST_BACKUP_BLOB_NAME` is owned by `storage::cloud::manifest_backup` with canonical value `manifest/manifest-backup.blob`; auth ceremonies no longer define their own manifest-backup cloud-path constant. Rationale: cloud-layout ownership belongs to storage, and shared callers now import one canonical contract anchor.
- `upload_manifest_backup` exports manifest snapshots with SQLCipher `VACUUM INTO` into the storage staging directory, encrypts with XChaCha20-Poly1305 (no AAD), uploads via `CloudTransport`, and removes export/staging artifacts on all error and success paths. Rationale: this matches the singleton-blob design and keeps manifest plaintext in zeroizing buffers.
- `download_manifest_backup` downloads ciphertext into staging, decrypts under `manifest_key`, atomically persists DB bytes to destination, validates with SQLCipher open + `PRAGMA integrity_check(1)`, and removes destination on integrity failure. Rationale: recovery must fail closed when backup bytes or keys are invalid.
- `recover_vault` and `recover_with_phrase` now delegate manifest restore to `download_manifest_backup` and map `ManifestBackupSyncError` to existing auth boundary errors (`InvalidCredentials` for crypto/integrity, `VaultHeaderInvalid` for transport/staging/persist). Rationale: preserves external ceremony error behavior while removing duplicated manifest import logic.
- Test support now uses real helper paths for nominal backup upload and a dedicated corruption helper for adversarial recovery tests. Rationale: maintain realistic round-trips while still supporting deterministic corruption-path assertions.
