## Deliverables

1. `CTX-ChaCha20-Poly1305` wrapper type in `src-tauri/src/sharing/ctx_aead.rs`:
   - Implement the AEAD interface using `chacha20poly1305` internally
   - Replace the transmitted Poly1305 tag with a 32-byte BLAKE3 commitment: `BLAKE3(b"arx-runa-ctx-v1" || key || nonce || ciphertext)`
   - Seal: run ChaCha20-Poly1305 encryption internally, discard the generated Poly1305 tag from the wire format, and append the 32-byte CTX commitment
   - Open: parse the final 32 bytes as the CTX tag, recompute the CTX commitment over `key || nonce || ciphertext`, reject if it does not match, and only then decrypt the ciphertext; no Poly1305 tag is serialized or verified on open
2. HPKE one-shot seal/open functions in `src-tauri/src/sharing/hpke.rs`:
   - Ciphersuite: `DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + CTX-ChaCha20-Poly1305`
   - Seal: `(enc, ct) = HPKE.Seal(recipient_pub, info=b"arx-runa-share", aad=b"", plaintext)`
   - Open: `plaintext = HPKE.Open(recipient_priv, enc, info=b"arx-runa-share", aad=b"", ct)`
   - Use `hpke` crate (v0.13.0) for all KEM/KDF operations
   - Wire format emitted: `[32B enc | ciphertext | 32B CTX tag]`
3. Share package creation in `src-tauri/src/sharing/packages.rs`:
   - Retrieve and unwrap `file_key` from SQLCipher `nodes` table using `key_encryption_key`
   - Assemble JSON payload: `share_id`, `file_id`, `file_name`, `chunk_count`, `chunk_size`, `chunk_uuids`, `file_key` (raw 32 bytes, base64), `sender_public_key` (owner X25519 public key, base64), optional `expires_at`, `cloud_endpoint`
   - Seal entire JSON payload as an HPKE envelope addressed to the recipient's X25519 public key
   - Export the resulting wire bytes as a `.vgshare` file
4. Share package import:
   - Parse wire bytes: read 32-byte `enc`, remaining bytes as HPKE ciphertext
   - Open with caller's X25519 private key via HPKE Open
   - Deserialise JSON payload; validate required fields; `expires_at` remains optional
   - Store in `received_shares`: `share_id`, `sender_contact_id`, `sender_public_key`, `file_name`, `file_key_wrapped` (wrap decrypted `file_key` immediately with local `key_encryption_key`), `chunk_count`, `chunk_size`, `chunk_uuids`, optional `expires_at`, `cloud_endpoint`, `imported_at`
5. Snapshot semantics: `chunk_uuids` is recorded at the moment the share package is created and is never updated; document as an explicit code comment in the package creation function
6. Test suite covering:
   - HPKE round-trip: seal with recipient public key, open with recipient private key, recover original plaintext
   - Wrong-recipient rejection: open with a different private key produces an authentication error
   - Corrupted ciphertext (single-byte flip in ciphertext body) is rejected by CTX commitment
   - Corrupted `enc` (single-byte flip in ephemeral key): open with correct private key fails (wrong KEM shared secret)
   - Share package JSON schema validation: missing required field (other than optional `expires_at`) produces an import error
   - `expires_at` round-trip: when present, survives serialisation into `received_shares` unchanged
   - Share package import → `received_shares` row contains correct `sender_public_key`, `file_key_wrapped`, and all other fields
   - CTX commitment rejection: modify a single byte of the CTX tag; open must return an authentication error

## Validation Checkpoint

**Automated tests**:
```bash
cargo test sharing::ctx_aead
cargo test sharing::hpke
cargo test sharing::packages
```
All tests must pass with no warnings.

**Manual verification**:
- Create a share package for a test file; inspect the raw bytes — first 32 bytes are `enc` (ephemeral public key); no explicit nonce follows
- Import the package on the same Arx Runa instance (using own public key as recipient); verify a row appears in `received_shares` with `sender_public_key` and `file_key_wrapped` populated

**Acceptance criteria**:
- HPKE open returns a distinct authentication error on any modification to `enc`, ciphertext body, or CTX tag
- Ephemeral private key is not retained in any struct field, static variable, or log output after KEM encapsulation (enforced by `hpke` crate internals)
- `file_key` in the share package is the same bytes as in the `nodes` table (no secondary encryption layer)
- On import, raw `file_key` bytes are wrapped into `received_shares.file_key_wrapped` and zeroized immediately after wrapping
- Snapshot semantics are enforced: `chunk_uuids` in the package matches the file's chunks at creation time; no live pointer to the current state of the file

## Implementation Notes

- Use the `hpke` crate (v0.13.0) with the `X25519HkdfSha256` KEM type and `HkdfSha256` KDF type; plug in `CTX-ChaCha20-Poly1305` as the AEAD type parameter
- The `CTX-ChaCha20-Poly1305` wrapper must implement the `hpke::aead::Aead` trait; tag length must be declared as 32 bytes
- Wire format: `enc` is always 32 bytes (X25519 public key); parse as `enc = bytes[0..32]`, `ct = bytes[32..]`; minimum valid length is 32 + 32 (enc + CTX tag) = 64 bytes with zero-length plaintext
- `file_key` in the JSON payload uses standard base64 encoding; decoded length must be exactly 32 bytes; reject at import time if length differs
- `sender_public_key` in the JSON payload uses standard base64 encoding; decoded length must be exactly 32 bytes
- `received_shares.file_key_wrapped` stores KEK-wrapped key bytes; wrap during import, then zeroize the raw key buffer
- `expires_at` is an optional Unix timestamp in the JSON; when absent or `null`, set `received_shares.expires_at` to NULL
- Do not use `x25519_dalek` directly in this sub-phase; the `hpke` crate manages the X25519 operations internally

## Security Review

**Required** — Invoke `security-reviewer` agent after implementation:
- HPKE correctness: `info` string is `b"arx-runa-share"`, `aad` is empty; no deviations
- CTX commitment: BLAKE3 domain string is `b"arx-runa-ctx-v1"`; key, nonce, and full ciphertext body are all committed
- No `file_key` plaintext appears in log output, error messages, or the exported `.vgshare` file outside of the HPKE-encrypted payload
- Authentication error paths: all three rejection reasons (wrong `enc`, corrupted ciphertext, wrong CTX tag) produce identical-looking `AuthenticationFailed` errors with no oracle information
