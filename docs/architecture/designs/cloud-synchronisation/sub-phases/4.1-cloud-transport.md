# Phase 4.1: CloudTransport Trait and Mock Implementation

**Parent roadmap**: [roadmap.md](roadmap.md)

**Depends on**: Phase 1 (cryptographic primitives), Phase 3 (chunking and manifest)

---

## Deliverables

1. `CloudTransport` trait definition in `src-tauri/src/storage/cloud/mod.rs` with `upload_blob`, `download_blob`, `delete_blob`, `list_blobs` methods
2. `CloudTransportError` thiserror enum with `NotFound`, `AuthenticationFailed`, `Timeout`, `IoError`, `RcloneProcessFailed`, `Other` variants
3. `CloudEndpoint` struct with `provider`, `bucket`, `region`, `endpoint`, `path_prefix` fields — serializable to JSON
4. `MockTransport` implementation using in-memory `HashMap<String, Vec<u8>>` backend for testing (store blobs keyed by remote path)
5. Full test suite for `MockTransport` covering all `CloudTransport` trait methods:
   - Upload → download round-trip
   - Delete removes blob
   - List returns correct paths under prefix
   - NotFound error on download of nonexistent blob
   - Idempotent upload (overwrite)
   - Idempotent delete (no-op on missing)

## Implementation Notes

- Use `#[async_trait]` for the trait (requires `async-trait` crate)
- `MockTransport` should use `Arc<Mutex<HashMap<String, Vec<u8>>>>` for interior mutability
- Remote paths use forward slashes (`/`) regardless of OS — validate this in tests
- `list_blobs` should filter by prefix correctly (e.g., `"vault/"` returns only paths starting with `"vault/"`)

## Implementation Decisions

- Adopted the canonical path-based `CloudTransport` surface in `storage/cloud/mod.rs` and migrated auth ceremony callers from `BlobName` + bytes to local-path/remote-path calls. **Rationale**: this is the phase contract anchor and keeps Phase 4.2/4.5 transport integration aligned. **Deferred follow-up**: none for this decision.
- Kept remote-path validation hardening deferred to Phase 4.2 (`RcloneTransport`) and did not introduce validated path newtypes in 4.1. **Rationale**: this run follows plan assumption #7 and avoids broad contract churn outside approved scope. **Deferred follow-up**: implement centralized path validation/newtypes in Phase 4.2.
- Kept pending-header concurrency serialization hardening deferred to Phase 4.3. **Rationale**: this run focused on trait migration and caller correctness, while pending-header lifecycle expansion is a documented later-phase concern. **Deferred follow-up**: add explicit serialization/locking or unique pending-header artifacts in Phase 4.3.
- Kept broader session-operation gate race hardening outside 4.1 scope after adding the missing `setup_recovery` operation guard. **Rationale**: the identified race is session-manager lifecycle architecture work beyond this phase deliverables. **Deferred follow-up**: address begin-operation fail-closed semantics in the auth/session roadmap track.
